# TikTok 楽曲 UGC 分析 — レポート完成までの手順（2026-09-11 版）

根拠: シルエット 880本での「答えを見ない」分類試験（`output/trial_silhouette/EVAL.md`）で、記事の主要な結論が
データのみから復元できた。この結果を根拠として採用する（ユーザー判断、2026-09-11）。

凡例: **[コード]** 決定論的に計算 / **[LLM]** 生成 AI（利用者の API キー） / **[人]** 利用者が WEBUI で判断

---

## 全体像

```
0 取得        楽曲 → 動画一覧 + 属性 + サムネイル                      [コード]   既存スクレイパーに属性追加
1 前処理      週次・特徴量・離陸週・層化サンプル                        [コード]   prep_sample.py 相当
2a 軸の提案   界隈 / フォーマット / 採用文脈 の候補                     [LLM]      classify_clean.md の前半
2b 軸の確認   統合・改名・追加                                          [人]       WEBUI
2c ラベル付け 全候補動画に 軸のラベル + 確信度 + 根拠                    [LLM]      バッチ・構造化出力
3 代表選定    段階の切り出し → 界隈×段階のセルに時間予算を配分           [コード→人] 12時間上限
4 コメント取得 代表動画のコメント + 返信                                 [コード]   spatest.py（Windows 機、要ログイン）
5 コメント分析 動画ごと → 界隈ごと に 動機・反応・引用                   [LLM]
6 レポート    章ごとに生成、人の考察を投入、章単位で再生成               [LLM+人]
```

利用者の待ち時間の大半は 0（約3秒/本）と 4（約3.5分/本）。2〜3 と 5〜6 は分単位。

## 0. 取得: 楽曲 → 動画一覧 + 属性 + サムネイル　[コード]

- 入力: 楽曲名（またはミュージックページ URL）
- 既存スクレイパーの経路（未ログイン・ヘッドレス・`__UNIVERSAL_DATA_FOR_REHYDRATION__`）をそのまま使い、
  **同じページ読み込みで属性を取り尽くす**（`analysis/enrich.py` の `extract()` を `scraper.py` に統合する）:
  - 数値: 再生・いいね・コメント・共有・保存・リポスト
  - 投稿者: uniqueId / nickname / **bio** / **認証** / **フォロワー数** / 動画数 / 総いいね
  - 文脈: 投稿地域 `locationCreated` / 本文言語 / **TikTok カテゴリラベル** / ハッシュタグ・メンション / **提案語** / 画面上の文字 / エフェクト
  - 動画: 尺 / 解像度 / **サムネイル**（URL が約24時間で失効するため画像をその場で保存）/ 音源 ID / 広告フラグ
- 出力: `videos.jsonl`（1行1動画、全属性）、`covers/<video_id>.jpg`
- 所要: 約3.2秒/本（880本で約47分）。既存 CSV も従来どおり出す
- 制約: 写真投稿はサーバー側データが無く属性が取れない（ToDo-1）。リストを寝かせると削除で欠ける（9か月で20%）ので、**取得は一度で完結させる**

## 1. 前処理　[コード]

- 週次の本数・再生数（`weekly.tsv`）、離陸週（週の本数が全体の5%を初めて超えた週）
- 分類対象の床: いいね ≥ 1,000 または 再生 ≥ 10,000（この段階では絞らない。LLM のラベル付けは安い）
- 層化サンプル（軸の提案用）: 再生上位100 + 最初期40 + 離陸後の各週から無作為6（seed 固定）
- サムネイルの一覧画像（20枚/枚、seq 番号付き）。LLM に個別画像を300回読ませない
- 実装済み: `analysis/prep_sample.py` / `analysis/build_llm_input.py`

## 2a. 分類軸の提案　[LLM]

- 入力: 層化サンプル（属性付き） + 一覧画像 + **他の楽曲の過去レポート**（分析の枠組みと語彙を学ぶ）
- 出力: `taxonomy.json` — `community`（界隈: 誰が）/ `format`（何をした）/ `motive`（なぜこの曲）の値と定義・見分けるシグナル、
  `region`（投稿地）/ `tier`（アカウント種別）の運用ルール。各軸に `unknown` を必ず含める
- **同じ楽曲について書かれた既存レポートは入力に入れない**（答え合わせにならないため。運用では新規楽曲なので通常は存在しない）
- 実装済みの指示書: `analysis/prompts/classify_clean.md`（前半）。シルエットでの提案結果: `output/trial_silhouette/clean/taxonomy.json`

## 2b. 軸の確認・修正　[人]

- WEBUI で値の統合・改名・追加・削除。例: `jp_talent` と `jp_influencer` を分けるか、`media_brand` の範囲
- 確定した軸にバージョンを付けて保存（レポート間で語彙を揃えるため、過去楽曲の軸を「雛形として読み込む」機能を持つ）

## 2c. 全候補動画へのラベル付け　[LLM]

- 入力: 床以上の全動画（属性 + サムネイル一覧）+ 確定した軸
- 出力: 1動画1行 — `community / format / motive / region / tier / conf(H,M,L) / reason(根拠にしたシグナル)`
- 実装方針: **Batch API**（非同期・半額）+ **構造化出力**（スキーマ強制）+ **プロンプトキャッシュ**（軸と指示を固定プレフィックスに）。
  Claude / ChatGPT の差はアダプタ1枚に閉じる
- 費用の目安: 1,000本 ≒ 150万トークン入力 → Opus 級で約10ドル、バッチで半分
- 品質の目安（シルエット実測）: H 57% / M 27% / L 16%。**高再生・最初期の動画は H に集中**するので、代表選定には十分。
  「界隈ごとの本数」を数字で断定する精度ではない（レポートでは「約」「主に」で書く）

## 3. 段階の切り出しと代表動画の選定　[コード → 人]

- 週 × 界隈 の構成表（本数・再生）を作る。**段階の境界はこの表から機械的に候補を出し**（界隈構成が入れ替わる週、離陸週、ピーク週）、
  LLM が名前を付け、人が確認する。段階の記述は表の言語化であって創作ではない
- 代表動画の選定（**再生数で一括に切らない**。シルエットではミャンマーの起点が再生数順59位、JO1 公式が84万で落ちる）:
  1. 時間予算（1ジョブ 12 時間）と 1本あたりの見込み時間（`API回数 ÷ 1.8回/分 + 15秒`。cap 120 なら約3.5分 → 約200本）から本数を決める
  2. セル = 界隈 × 段階。各セルに **最低2本**（そのセルの最初期1本 + 最大再生1本）
  3. 残りをセルの規模の**平方根に比例**して配分（規模差10倍でも配分は3倍）
  4. 常に含める: 全体の最初期 N 本、公式・本人アカウント、全体上位3本、公式企画ハッシュタグ付き
  5. 「再生数順では落ちるが動線上重要」な動画をリストで示す（シルエットの例: `clean/pathway.md` 第5節の17本）
- 人が WEBUI で追加・除外。確定リストと予想所要時間を表示。残りは次のジョブで続き（`--resume` 相当）

## 4. コメント + 返信の取得　[コード / Windows 機]

- 前提（決定済み）: 利用者ごとの捨てアカウント。ログインは**画面転送**（CDP screencast、ID/パスはサーバーが入力、
  CAPTCHA は利用者が画面で操作、認証コードは利用者がフォーム入力）。実際のログインで出たのはメールの認証コード
- 実行: `spatest.py --videos <代表リスト> --replies --cap 120 ...`（引き継ぎ書 第9章の引数）。Windows 機 `BELLE-DESKTOP01` の対話セッション Chrome（9222）
- ジョブは直列（IP 律速）。待ち行列の位置と予測開始時刻を表示
- 必ず見るログ: `描画状態: visible / フレーム>0`、`SPA=はい`、`aweme_id == video_id`（混入0）、20件ちょうどで止まっていないこと
- 出力: 動画ごとの `comments.jsonl`（37フィールド/コメント + 返信）

## 5. コメント分析　[LLM]

- **動画ごと**（構造化出力）: この界隈がなぜこの曲を取り上げたと読めるか / 視聴者の反応の型（懐かしさ・難易度・比較・本家探し…）/
  代表的コメントの引用（**cid 付き**。レポートの「このコメントが4,000いいね」を元データに辿れるように）/ 公式・本人の返信 / 言語・地域
- **界隈ごと**: 動画ごとの結果を束ねて、共通する動機と段階間の変化を要約
- Batch API。1本 ≒ 1万トークン → 200本で約10〜15ドル

## 6. レポート生成　[LLM + 人]

- 章構成は過去レポートに揃える: 分析方針 → 拡散経路（段階 × 代表動画 × 数値）→ 界隈ごとの分析（コメント根拠）→
  なぜバズったか（**人の考察を入力**）→ 結果 → 再現性
- 入力: 3 の表と代表リスト、5 の要約、過去レポートの体裁、人の考察（自由記述）
- **章ごとに生成し、章単位で再生成**。数値は 1〜3 の表から引用し、LLM に計算させない
- 出力: Markdown（note 貼り付け用）。埋め込み動画は URL リストで別出し

## 6b. 知能の供給源（API 課金をしない利用者への提供。2026-09-12 決定）

サービス本体は「データと道具」に徹し、LLM をどこから持ってくるかは利用者ごとの設定にする。
成果物（軸・ラベル・分析・レポート）とプロンプト（`analysis/prompts/`）は3経路で共通。

| 経路 | 利用者が持つもの | 仕組み | 向く工程 |
|---|---|---|---|
| ① API キー | Console のクレジット | サーバーが自動実行（Batch・構造化出力・キャッシュ） | 全工程を無人で |
| ② チャット + カスタムコネクタ | claude.ai Pro/Max、ChatGPT Plus | サービスが **MCP サーバー**（公開到達可、利用者認証と紐付け）を出し、利用者がコネクタ登録。チャットから道具を呼ぶ | 軸提案・修正・コメント分析・執筆（対話的な工程）。全件ラベル付けは重いので層化サンプルに絞る |
| ③ 手元の Claude Code（Claudian 型） | Claude Code が使える定額 | ②の道具を Claude Code から呼ぶ。リポジトリ同梱のスキルで一括処理 | 全件ラベル付けなど量の多い工程 |

根拠: カスタムコネクタは Free/Pro/Max/Team/Enterprise で利用可（Free は1個）。Claude Code は Pro/Max で公式に利用可。
Pro プランに API は含まれない（Console で別課金）。

## 6c. 過去レポートの持たせ方（層1 + 層2）

- 著者の note 記事は 89本・約88万字（≒70〜95万トークン）。生で全部入れると楽曲データと合わせて窓を溢れ、参照精度も落ちる
- **層1**: 記事群から一度だけ蒸留した知識ベース（記事カード1本1行・概念辞書・文体ガイド。5〜8万トークン）を毎回投入（キャッシュ）
- **層2**: 新規楽曲に近い過去レポートを全文で 5〜8本
- 対象楽曲に言及する記事は必ず除外（`output/notes_corpus/INDEX.json` の `taboo_hits` で機械判定）
- 蒸留の指示書: `analysis/prompts/distill.md`。成果物: `output/notes_corpus/distilled/`

## 6d. サーバーの GPU（RTX 4080 SUPER 16GB）の使いどころ（案、未検証。2026-09-12）

| 案 | 内容 | 効く理由 |
|---|---|---|
| 1 音源の切り出し箇所 | UGC の音声を原曲とクロマ相関で照合し「原曲の何秒〜何秒」を出す | 過去レポートの柱（Riser＋ブレイク、サビ前）を全件で数値化。要: 動画取得（`playAddr`）＋原曲音源 |
| 2 コメントの埋め込み・反応分類 | bge-m3 等で全コメントを埋め込み、7〜14B の量子化モデルで反応の型を全件に付与 | 「上位20件を読む」→「全件の分布」。この部分は無料化できる |
| 3 姿勢推定でフォーマット判定 | RTMPose 等で手の軌跡を取り、起点動画との類似度で「同じ振付／亜種／別物」 | notes.md の穴（サムネでは動きが分からない）を埋める |
| 4 OCR・Whisper | 動画フレームの字幕、コント・解説の書き起こし | 分類材料の追加 |
| 5 内蔵小型モデル | 無料利用者向けに粗いラベルを付け、低確信度だけ利用者の Claude へ | 4つ目の知能の供給源 |

使わない: 描画補助（実画面あり）、大型 LLM の本番実行。環境は Windows のまま Ollama / llama.cpp（CUDA）。順番は 1 → 2。

## 7. 品質保証（新規楽曲でどう確かめるか）

- 既存レポートのある楽曲で運用前検証をする場合: **その楽曲の記事は LLM に見せない**。事前知識を先に申告させ、
  結果を記事と照合する（`analysis/compare_clean.py` の型）。シルエットの結果: `output/trial_silhouette/EVAL.md`
- 運用時（記事なし）は、2b と 3 の人の確認が品質の砦。conf L の動画は代表に選ばれにくくする

## 8. End-to-End 納品物テストの結果と、確定したポリシー（2026-09-12〜14）

**シルエット（880本）で、記事を読んでいない AI が「分類 → 代表選定 → コメント取得 → コメント分析 → 執筆 → 仕上げ」を通し、
著者の記事と比較した。結論: 拡散経路・界隈・公式の位置づけ・なぜ広がったかは記事と同じ結論に、根拠（cid・seq・数値）付きで到達。
届かないのは 音楽面・時代背景・TikTok 外・他楽曲への一般化（＝人の考察の領域）。** ユーザー判断: この方式で進める。

| 成果物 | 場所（`output/trial_silhouette/e2e/`） |
|---|---|
| 採点（8観点、A4 B5 C5 D4 E3 F4 G5 H5） | `E2E_EVAL.md` |
| レポート（内部 ID 付き） | `report/REPORT.md` |
| **note 貼り付け用**（動画 URL 23本を単独行、内部 ID なし） | `report/NOTE_DRAFT.md` → `NOTE_BODY.md`（本文）/ `NOTE_TITLE.txt` |
| 著者が書き足す箇所の一覧 | `report/EDITOR_NOTES.md` |
| コメント分析（動画ごと JSON・界隈統合・返信の価値） | `report/video_analysis.jsonl` / `community_synthesis.md` / `reply_value.md` |
| **人間の記事との比較**（81要素、種別つき、結論が違う10点） | `COMPARISON.md` |
| コメント数のアブレーション | `ABLATION.md`（入力 `comments_cap20|40|80|noreplies/`、出力 `ablation/*/`） |

### 確定したポリシー

- **コメント取得量**: 標準 40件（主たる反応は20件で96%・40件で100%一致）。起点・本家・公式・解説・大型ヒットは120件。
  返信は界隈で切り替え: showcase 系（タレント・インフルエンサー・家族・学生日常）は返信なし、それ以外は「返信数上位3件＋質問形の親＋本人・公式のコメント」の返信を各5件まで。
  1本約3分 → 12時間で約240本。`spatest.py` の `--reply-min` を質問形に対応させる実装は未着手
- **代表動画の選定**: 界隈×段階のセル。起点動画は必ず含める（今回はグリッドに出ず落ちた → 公式の初動を誤認した。`COMPARISON.md` #5）
- **段階の分割**: 段階5（コメント分析）と段階6（執筆）は別プロセス（文脈50万トークン超を避ける）。段階6の後に**仕上げ**（内部 ID 除去・動画 URL 単独行・試験用語除去）と**比較／採点**を置く
- **層1/層2**: 82本を蒸留した知識ベース（`output/notes_corpus/distilled/`: GLOSSARY 4.0万字・STYLE_GUIDE 1.0万字・cards 82行・README。約10万字）を毎回投入、近い過去レポート全文 6〜8本を追加。対象楽曲に触れる記事は `INDEX.json` の `taboo_hits` で機械除外
- **評価の作法**: 同じ楽曲の記事を読んだプロセスで分類・執筆してはいけない。各担当に事前知識を先に申告させる。採点者だけが記事を読む
- **note への投入**: プレーンテキストで貼れば note が Markdown を変換する（VS Code からのコピーは HTML が混ざるので `pbcopy < NOTE_BODY.md`）。URL 単独行は埋め込み。一括貼りで埋め込みにならない場合は `analysis/md2note.py`（段落ごとに貼る。公開はしない）— **note 実エディタでは未検証**

### 判明した AI 側の弱点（次の実装で直す）

1. 起点動画のコメントが取れず「公式の初反応は10/24」と書いた（実際は 8/10 に起点動画へ公式コメント）→ 起点は必ず取る
2. 「なぜ今流行」系の質問（126件）の返信が返信数≥10の閾値で取れていない → 質問形は返信1件でも取る
3. THE FIRST TAKE の再生数（人間 100万／AI 1,000万＝公式投稿本文）が食い違う → 外部指標は取得元を明記
4. 豪州動画を人間側が国内派生と誤配置していた例もある（AI が正しい）→ 地域属性は人間の目視を補正できる

### 他ワークフローへの当てはめ（叩き台）

- **2 特定動画**: A3 → A4（1本、返信厚め）→ C4（動画1本の深掘り）→ 「どこから来た視聴者か」（コメント言語・提案語）→ C5。**新規**: その動画の投稿者の直近投稿（A5）との比較、同音源・同タグの前後関係（A2 の部分実行）
- **3 特定アカウント**: A5 → A3（全投稿）→ B1（時系列）→ 2 を代表数本に適用 → C5（アカウントの時系列として束ねる）。**新規**: 投稿間の変化点検出、フォロワー推移（外部）
- **4 YouTube**: A1〜A5 を YouTube Data API 実装に差し替え（コメント・返信も API で取れる → A4 の実画面・ログインの制約が消える）。B〜E はそのまま。**層1 の YouTube 版記事**（著者は YouTube 分析回も書いている）は cards の `platform` で選別できる

### 整理の方針で決めること（次チャットの論点）

- 小機能の境界: 「取得（プラットフォーム依存）」「整形（依存なし）」「LLM（依存なし、プロンプト＋スキーマ）」「評価」の4層で切るか
- 中間データの形式: 動画・投稿者・コメントの共通スキーマ（TikTok/YouTube を吸収）。第8章で実装された `store.py` との関係
- ワークフロー定義の書き方: 小機能の DAG を設定ファイルで並べる（例: YAML）か、Python で組むか
- LLM 呼び出しの共通化: 入力を Markdown/JSON に整形 → プロンプト → 構造化出力、の型。知能の供給源（API／コネクタ／Claude Code）を差し替えられるアダプタ
- 「答えを見ない評価」を各ワークフローでどう再現するか（記事があるケースのみ）
