**アプリのUIを押して、アプリが受け取ったJSONを横取りする。**

## 2. 検証済みの事実（再検証不要）

### 2-1. ログインが必須

同一ブラウザ・同一コード・同一動画で、**変数をログインCookieだけにした統制比較**を実施:

| | 未ログイン | ログイン済み |
|---|---|---|
| ページ描画 | `ready:complete` / いいね7869・コメント数18を正しく表示 | 同左 |
| コメント本文要素 | **0個**（スクロールしても0） | 描画される |
| コメントAPI | **HTTP 200 / 0バイト** | **成功** |

ブラウザが実物か自動化かは**無関係**だった（当初この交絡要因を見落とし、再検証で排除済み）。

### 2-2. ブラウザの用意方法が独特

**Chromeを直接起動し、Seleniumは「接続」する。**

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --user-data-dir="$HOME/.tiktok-ugc-profile" --profile-directory=Default \
  --remote-debugging-port=9222 --no-first-run --no-default-browser-check \
  --mute-audio "https://www.tiktok.com/" &
```

```python
o = webdriver.ChromeOptions()
o.debugger_address = "127.0.0.1:9222"
d = webdriver.Chrome(options=o)     # 起動ではなく接続
```

**理由**: ChromeDriverに起動させたChromeは、既に存在するプロファイルのCookieを
**復号できずログイン状態を引き継げない**（macOSのKeychain由来と思われる。実測で確認）。
手動ログインは1回だけでよく、セッションは数時間〜数週間持続する。

### 2-3. コメントアイコンのクリックが必須

動画ページを開いただけでは、**ページはコメントAPIを一度も呼ばない**
（実測: 全161リクエスト中、コメントAPI 0件。コメント欄も未描画）。

`[data-e2e="comment-icon"]` をクリックすると、その瞬間に
ページ自身が署名付きリクエストを投げ、**HTTP 200 / 60,849バイト**が返る。

### 2-4. 署名はページに任せられる

TikTokは自前で `window.fetch` をラップしており、**同一オリジンのfetch呼び出しに
`X-Gnarly` / `X-Dynosaur` を自動付与する**（送信URLを捕捉して実測確認）。

つまり**署名の扱いを実装側で考える必要はない**。ページに投げさせればよい。

### 2-5. サブリソースのブロックが有効

CDPで画像・動画・フォント・テレメトリを止めると、
**ページ読み込みが12〜16秒 → 1.6秒**に短縮された。TikTok側の負荷も減る。

```python
d.execute_cdp_cmd("Network.enable", {})
d.execute_cdp_cmd("Network.setBlockedURLs", {"urls": [
    "*.jpg","*.jpeg","*.png","*.webp","*.gif","*.svg","*.ico",
    "*.mp4","*.m4a","*.m4s","*.ts","*.m3u8","*.webm",
    "*.woff","*.woff2","*.ttf","*.otf",
    "*mon-sg.tiktokv.com*","*/monitor_browser/*","*/monitor_web/*","*analytics*",
]})
```

### 2-5b. SPA遷移ならブロックされない（2026-09-08 夜に確認）

楽曲ページを1回だけ開き、以降は**グリッドのリンクをクリックして動画へ移動**すると、
`driver.get()` 方式で3〜4本だった壁が**20本連続**まで伸びる（→ 第7章の検証結果）。

SPA遷移で分かった付随的な事実:

| | `driver.get()` 方式 | SPA遷移方式 |
|---|---|---|
| 1動画あたりの付随リソース | 37〜161件（ブロック無効時） | **0件**（読み直さない） |
| コメントアイコンのクリック | **必須**（2-3のとおり） | **不要**。開いた時点でページが自分でコメントAPIを呼ぶ（20/20本） |
| 1動画あたり所要 | 15.7秒 | 17.0秒 |

**リソース0件が本質と思われる**。フルロードのたびにTikTokは37〜161件の要求を受けるが、
SPA遷移ではコメントAPI 1件しか飛ばない。ブロックは「動画を見た回数」ではなく
**「フルロードした回数」**でトリガーされていた可能性が高い（2-6の「回数でトリガー」という
記述は、正確には「フルロードの回数」と読むべき）。

### 2-5c. 楽曲ページのDOM（現行ビルドで実測）

- **モーダルは存在しない**。`browse-close` / `browse-video-desc` はいずれも0件で、
  リンクをクリックすると動画ページそのものへ遷移する。戻るのは `history.back()`
- **実マウスイベントではクリックが通らない**。リンクの中心にあるのはホバープレビューの
  `<video>` 要素で、ネイティブクリック・ActionChains・CDPの `Input.dispatchMouseEvent` は
  いずれも遷移しない（いずれも例外は出ないので、失敗に気づきにくい）。
  **リンク要素そのものに `click` を送る方式でのみ遷移する**
- グリッドは1動画につきリンクが2本ある（サムネイルと説明文）。href で重複を除くこと

### 2-6. ブロックの挙動（最重要）

| 条件 | 結果 |
|---|---|
| 動画ページを間隔ほぼ0秒で開く | **3件目でHTTP 403** |
| 動画ページを**間隔60秒**で開く | **4件目でブロック** |
| 回復までの時間 | **約1.5時間** |
| ブロック中のトップページ | 正常に開ける |
| ブロック中の既存スクレイパー（未ログイン） | **影響なし** |

**間隔を60倍にしても止まる本数がほぼ同じ** = 頻度ではなく回数でトリガーされている。

ブロック時の見え方は2種類:
- `HTTP 403` ページ（JSが実行不可になる。`SecurityError` で検知できる）
- `"Please wait..."` チャレンジ画面（**SPA初期化中に一瞬出るので、25秒以上継続した場合のみ**ブロックと判定すること）

### 2-7b. 1リクエスト50件は「旧方式の数字」（混乱しやすいので注記）

第6章に「1リクエストの返却件数 最大50件」とあるが、これは
[collect.py:217](../../../tiktok-overnight/collect.py) が `count` に **50を明示的に渡していた**
自前リクエスト方式の実測値。**現行のページ操作方式には適用されない。**

現行方式ではリクエストを組み立てるのはページなので、**ページが要求する20件が上限**になる。
同じ100件を取るのに旧方式は2リクエスト、現行は5リクエスト。
この2.5倍が「署名を自作しない」ことの対価。

`count` を50に書き換えて投げ直すのは**第4章の「捕捉した署名を別パラメータに
付け替えて投げ直す」に該当する**ので採らない。

### 2-9. ブラウザの描画が止まると1動画20件で頭打ちになる（最重要の落とし穴）

**TikTok側の制限ではない。こちら側の問題。** 2026-09-09に判明。

Chromeウィンドウが**他のウィンドウに隠れる**と、Chromeは描画を止める（最小化していなくても起きる）。
すると連鎖的に:

1. `requestAnimationFrame` が発火しない（実測: 1秒で**0フレーム**）
2. `document.visibilityState` が `hidden` になる
3. `IntersectionObserver` が発火しない
4. コメントの仮想リストが `DivVirtualItemSkeleton` のまま実体を描画しない
   （1項目100pxの空プレースホルダ。パネルは「2093件のコメント」と出るのに中身が真っ白）
5. 「次を読む」判定に到達せず、**1動画20件で頭打ち**

**見分け方**: コメント欄の容器の高さ。20件で `scrollHeight ≈ 2054`（＝1項目103px）なら
スケルトン。実体が描画されていれば `≈ 2957`（＝1項目148px）。

**対処**:

```python
d.execute_cdp_cmd("Emulation.setFocusEmulationEnabled", {"enabled": True})
```

これで `visibility=visible` / フレームが回り出し、スケルトンが実体に置き換わる。
**TikTokに送る内容は何も変わらない**（自分のブラウザに描画を続けさせるだけ）ので、
第4章の偽装には当たらない。

`Page.setWebLifecycleState(active)` と `Browser.setWindowBounds` は**効かなかった**。

`spatest.py` は起動時に `check_rendering()` で描画が動いているか確認しログに出す。
**この行を必ず見ること。** 止まったまま走らせると、ブロックもエラーも出ないまま
全動画が20件で終わる。

### 2-10. 隣の動画のコメントが混ざる（データが1本ずれる）

動画ページは**次の動画のコメントを先読みする**。素直に「クリック直前にフックをリセットして
捕捉する」と、その動画自身のぶんは前回の先読みで既に取得済みのため新しい要求が飛ばず、
**次の動画の先読みだけを拾う**。

実測（修正前）: 20本走行で**19本が完全に別動画のデータ**。1本目のみ半分正しい。
ブロックもエラーも出ないので、`aweme_id` を照合しない限り気づけない。

**対処**: リセットせず、捕捉したコメントを `aweme_id` ごとに仕分けて溜める。
先読みぶんはその動画の1ページ目として使えるので、むしろ得になる。

**検算**: 出力の各コメントの `aweme_id` が、その行の `video_id` と一致するか必ず確かめること。

### 2-11. ページは同じコメント要求を2回投げる（要求の半分が無駄）

コメント欄をスクロールして次ページを読ませると、ページは**同一の要求を約100ms差で2回**投げる。
実測（`dup4_summary.json`）: パス `/api/comment/list/`・`aweme_id`・`cursor`・`count` が
すべて同一の組が、cursorごとに必ず2件ずつ。

**こちらの操作が原因ではない**（切り分け済み）:

| 疑ったもの | 結果 |
|---|---|
| スクロールの送り方（300px跳躍 / 30px小刻み / なめらかスクロール） | **3方式ともきっかり50%**。無関係 |
| コメントパネルの二重マウント | DOM上に `DivCommentMain` は**1つだけ**。無関係 |
| フックの二重記録（`fetch` と `XHR` の両方で拾う） | 両方とも `via=fetch`、送信時刻も応答件数（18/19）も別。**本物の重複** |

**対処**: フックで**要求の合流**を行う。同じキー（パス＋`aweme_id`＋`cursor`＋`count`＋`reply_id`）の
要求が飛行中なら送らず、1件目の応答から作った同じ中身の応答を2件目に渡す。

効果（実測）:

| | 抑制なし | 抑制あり |
|---|---|---|
| 重複率 | 48〜50% | **14%** |
| 要求効率 | 2,280件ぶん要求 → 1,178件 | **140件ぶん要求 → 137件** |
| 1動画あたりの要求（100件取得時） | 11.4回 | **7.0回** |
| 50本の所要（2回/分） | 4.8時間 | **2.9時間** |

**これはページの挙動への介入にあたる**が、方向は「余計に取る」ではなく
**TikTokに届く要求を半分に減らす**side なので採用した。取得内容は変わらない
（混入0件・重複cid 0件を確認済み）。

### 2-12. `sort_tags.top_list` が「上位コメント」の印（どこまで取ればよいかの判断基準）

コメントの並びは**いいね降順ではない**。TikTokの関連度ランキング順で、
`sort_tags` の `top_list=1` が付いたものが上位リスト。これが尽きると
いいね0〜2の尾部（反応の無いコメント）が続くだけ。

実測（100動画）:

| 上位リスト件数 | 動画数 |
|---|---|
| 0〜20件 | 9本 |
| 21〜50件 | 22本 |
| **51〜100件** | **60本** |
| 101〜200件 | 3本 |
| 201〜400件 | 3本 |

中央値88件・最大345件。**94%の動画は100件以内に収まる。**

**注意: 件数で打ち切ってはいけない。** 並びがいいね降順でないため、
いいね4104のコメントが220番目に現れる例がある。上限100件で切ると
「いいね100以上のコメント」の25〜33%を落とす（実測）。

`spatest.py` は上位リストが尽きたら自動で止まる（`--min-comments` が下限、
`--cap` が安全弁）。**件数ではなく上位リストで止めること。**

#### 上位リストの範囲は実行ごとに変わる（2026-09-11 に判明。仕様として受け入れ済み）

同じ動画を2回取ると、先頭100件のうち同じ位置に同じコメントがあったのは13件だけ。
上位リストの長さも98件→310件と変わった。TikTok側のランキングが動的なため。

**これは問題にしない**（ユーザー判断）。運用では同じ解析を繰り返さないので、
「その時点の上位リストを取り切る」で十分。**取り直して件数が違っても不具合ではない。**
一方で「上位リストを取り切った本数」は事後検証できない。走行ログの判定はその時点のもの。

### 2-13. 返信の取得（2026-09-11 に方式確立）

当時の自前リクエスト方式は使えないが、**ページのUIを押せば取れる**。

| 手順 | UI | 結果 |
|---|---|---|
| ① 開く | 「N件の返信を表示」（`[class*="TUXButton-label"]`） | `cursor=0` で**3件**返る |
| ② 続き | 「あとM件表示」 | `cursor=3, 6, …` で3件ずつ |
| ③ 畳む | 「非表示」 | 次のコメントを操作する前に必ず畳む |

- エンドポイントは `/api/comment/list/reply/`、**`count=3` 固定**
- 返信は `reply_id` に**親コメントID**が入る（本体は `reply_id='0'`）。
  第8章の「`parent_comment_id` で自己参照」がそのまま使える
- `aweme_id` は本体と同じなので、**`reply_id` で本体と返信を分けること**

**実装で踏んだ罠（すべて `spatest.py` で対処済み。同じ穴を掘らないこと）**

| 罠 | 症状 | 対処 |
|---|---|---|
| 本体収集の直後はパネルが**最下部**にいる | 仮想リストの画面外にはボタンが無く、10本中8本で返信0件 | 開始前に最上部へ戻す |
| 畳むと「N件の返信を表示」が**復活**する | 同じコメントを無限に開く | 処理済みの項目に印を付けて飛ばす |
| 「あとM件表示」が画面に複数残る | どれが誰のものか分からない | いま開いている項目の中だけを探す |
| 1コメントの上限判定に**動画全体の累計**を使った | 2コメント目以降が3件で止まる | 開く前との差で判定 |
| 総数の読み取りが返信のレスポンスを拾う | 「上位300件 / 総数73」のような表示 | `reply_id='0'` のレスポンスだけ見る |

**残っている小さな不具合**: 5コメント中1件が3件で止まる（11件あるうち）。
「あとM件表示」を1回押した後に続きが見つからないケース。頻度を見てから対処する。

実測分布（100動画・10,646コメント）:

| | |
|---|---|
| 返信を持つコメント | 1,459件（15%） |
| 返信の総数 | 4,050件 |
| 本体レスポンスに同梱される返信 | 485件（全返信の12%）＝**無料で取れている分** |

### 2-8. コメントAPIには独自の上限がある（2026-09-08 夜に判明）

第2章の旧版は「コメントAPI自体のレート制限は未確認」としていたが、**存在する**。

深いスクロールは1動画あたりのコメントAPI呼び出しを10〜16回に増やす。
約30分でおよそ50回を超えたあたりから、コメントAPIが**HTTP 200 / 0バイト**を返し始めた。

このときの状態（切り分け済み）:

| 見るもの | 状態 |
|---|---|
| 楽曲ページ | **正常**（動画リンク108件、チャレンジ画面なし） |
| ログイン | **維持**（`sessionid` / `sid_tt` / `uid_tt` すべて存在、有効期限2027-03） |
| コメントAPI | **HTTP 200 / 0バイト** |

つまり2-6の「動画ページのブロック」とは**別の制限**。ページは開けるがコメントだけ返らない。
0バイト応答を見たら、署名方式を疑う前に**まずこれを疑うこと**（第5章の誤診1と同じ形）。

**回復時間は未計測**。計測するには繰り返し試行が必要で、それは第4章の

## 4. 方針として採らないもの（技術的可否ではなく判断）

**これらは「試したが駄目だった」ではなく「やらないと決めた」もの。**
実装を急ぐあまり踏み込まないこと。

| やらないこと | 理由 |
|---|---|
| `navigator.webdriver` 等の**自動化マーカーを偽装**する | ボット検知そのものを欺く行為。一度スクリプトを書いたが破棄した |
| `webmssdk.js` を難読化解除し、**`X-Gnarly` のアルゴリズムを再実装**する | 同上。ボット対策のリバースエンジニアリング |
| 捕捉した署名を**別パラメータに付け替えて**投げ直す | 発行対象と異なる要求への署名流用 |
| **レート制限の閾値を探索**するツールを作る | 403はTikTok側の明示的な停止シグナル。不正利用対策の較正にあたる。代わりに**許容総時間から逆算して間隔を決める** |
| 住宅プロキシでIPを分散する | 有料であり、かつ検知回避が目的になる |

**採ってよい**のは「ページ自身に操作させ、その結果を受け取る」方式。
署名も要求の組み立てもページに任せる。これは偽装を含まない。

> **注意**: 上記に該当するコードは、開発環境の安全機構によって**実行がブロックされる**。
> 調査の後半では正当なスクリプトまで巻き込まれて実行できなくなったため、
> **実行はユーザー側で行った**。新任者も同様の制約を受ける可能性がある。

### ペースの律速はどこか（2026-09-10 に確定。ここは再調査不要）

**結論: `--calls-per-min` を 2.5 より大きくしても実際のペースは上がらない。**

#### 設定値と実績（実走3回）

| 設定 | 実績 | 設定に対する割合 |
|---|---|---|
| 1.8回/分 | 1.14回/分 | 63% |
| 2.0回/分 | 1.44回/分 | 72% |
| **4.0回/分** | **1.95回/分** | **49%** |

設定を2.0→4.0と倍にしても、実績は1.44→1.95（+35%）しか動かない。
**構造上の天井は約2.1回/分**（1動画5.7回 ÷ 161秒）。

#### 時間がどこに消えているか（100本走行の実測）

| | 本数 | 所要 | API | スクロール | 取得 |
|---|---|---|---|---|---|
| 上限100件に到達 | 61本 | 148秒 | 7.0回 | 45段 | 129件 |
| 上限未満で終了 | 38本 | 131秒 | 3.6回 | 67段 | 51件 |

内訳:

- 上限到達: 148秒 = **ペース待ち105秒**（7回×15秒）+ 残り43秒
- 上限未満: 131秒 = ペース待ち53秒 + **残り77秒**

「残り」は主に**打ち切り判定の尻尾**。底に着いてから
`stall_limit`(12段) × (`max_nudges`+1)(4回) = 最大48段、1段1秒で約48秒を、
データが増えないまま消費している。上限未満で終わる動画ほどここが長い。

#### 速くしたい場合に触るところ

**`--calls-per-min` は触っても無駄**（2.5以上にしても天井は変わらない）。触るならこちら:

| 引数 | 既定 | 効果 |
|---|---|---|
| `--stall-limit` | 12 | 底で粘る段数。減らすと尻尾が短くなるが取りこぼす |
| `--max-nudges` | 3 | 下り直しの回数。同上 |
| `--step-pause` | 1.0 | 1段の待ち。減らすと全体が速くなる |

ただし**取りこぼしと引き換え**になる。`total` と `has_more` を必ず記録して、
削りすぎていないか確かめること（2-11参照）。

| 出来事 | 平均 | 瞬間最大（60秒窓） | 結果 |
|---|---|---|---|
| 2026-09-08 夜の空応答 | 約1回/分 | 約6回/分 | **空応答**（累積60回時点） |
| 50本走行（暴走あり） | 2.58回/分 | **11回/分が363箇所** | ブロックなし |
| 100本走行 | 1.95回/分 | 5回/分 | ブロックなし |

**11回/分の窓が363箇所続いてもブロックされなかった**ので、
瞬間的なバーストへの耐性はかなり高い。09-08の空応答は
バーストよりも累積量か、当時の別要因（暴走リトライ）による可能性が高い。

**それでも閾値を測りにいかないこと**（第4章）。空応答を踏んだら即中断して

#### 破棄した旧方針とその理由（同じ制約を復活させないこと）

旧版はここに「**制約**: 認証情報をこちらで預かってはいけない」と書いていた。**これは撤回する。**

- **理由が接続していなかった。** 「第10章のとおりリスクがIPbanではなくアカウント凍結に移るため」
  という根拠は「**本人アカウントを使わせない**」は支えるが、「**認証情報を預からない**」を
  全く支えていない。第10章を読み返しても、認証情報の預かりについては一言も書かれていない
- 実態は、当時の前提（**手元のMacで人間が操作する**）では認証情報を預からないコストが
  ゼロだったため、**現状の説明が制約に格上げされていた**もの。値札がついていなかった
- サーバーがディスプレイレスになり利用者が遠隔になった時点で、この制約の値段は跳ね上がる。
  ユーザーは**預かってよい**と判断した

預かることの実務的なコスト（漏洩時の責任・ログに載りうる・TikTokの規約上パスワード共有が
問題になりうる）は依然として存在するが、**絶対の制約ではなく天秤に載せるコスト**として扱う。

#### 確定した前提（ユーザー判断。覆さないこと）

1. 利用者それぞれが**自分で捨てアカウントを用意する**
2. **サーバーがそのアカウントでログインして**コメント取得を走らせる
3. 利用者が触れるのは**WEBUIのみ**。サーバーには一切触らせない
4. サーバーの実体は**モニタ無しで常時起動するWindows機**
5. 本人アカウントは使わせない（第10章。ここは維持）

**どの方式を選んでも、最終的にセッションCookie（＝アカウントへのフルアクセス権）はサーバーに残る。**
アーキテクチャ上避けられない。差が出るのは「パスワードまでサーバーを通るか」と
「CAPTCHA・2段階認証を突破できるか」だけ。

#### 採る方式: 画面転送（CDP screencast）

サーバーがログインページを開き、CDP `Page.startScreencast` の画像をWEBUIへ流し、
クリックを `Input.dispatchMouseEvent` で返す。**本物のTikTokログイン画面をWEBUI越しに操作させる。**

入力の分担でIME問題を回避する:

| 入力するもの | 誰がやるか | 理由 |
|---|---|---|
| ID・パスワード | **サーバーが自動入力**（`Input.insertText`） | 通常ASCIIなのでIMEが要らない |
| CAPTCHA（スライド・回転） | **利用者が画面転送で操作** | マウス操作なので文字入力が発生しない |
| 2段階認証コード | 利用者がWEBUIのフォームに入力 → サーバーが流し込む | 数字なのでIMEが要らない |

**CDPのキーイベントではIMEを扱えない。** 日本語入力が必要な経路を作ってはいけない。

#### 採らない方式と理由

| 方式 | 採らない理由 |
|---|---|
| **QRコードログイン** | tiktok.com/login に「Use QR code」は**存在する**（2026-09-11 確認）。パスワードが一切サーバーを通らず、CAPTCHA・2段階認証も丸ごと回避できるので技術的には最良だった。**しかし捨てアカウントを利用者のスマホのTikTokアプリに入れる必要があり、本垢と同一端末に同居する。** 捨て垢のBANが本垢に波及するかは**実証データが無く不明**だが、不確かなら安全側に倒す（ユーザー判断）。画面転送なら捨て垢は**サーバーのブラウザにしか乗らない** |
| ID/パスをフォームで受け取り、自動ログインだけする | **CAPTCHAに当たった時点で行き止まり。** 自動突破は第4章の禁止領域。突破しないなら結局CAPTCHAを利用者に見せる仕組み＝画面転送が要る。「実装が軽い」という期待が成立しない |
| Cookieを利用者に書き出させて貼らせる | 拡張機能の導入が要り、前提3（WEBUIのみ）に反する。IP変更でセッションが無効化される可能性も未検証 |
| リモートデバッグポートをトンネルで公開し、利用者のPCのChromeに繋ぐ | デバッグポートは**そのブラウザの無制限操作権**。公開した時点で認証情報を預けるより危険 |

#### ヘッドレスは使わない

**「ヘッドレス検知をされないようにする」のではなく、検知されるような状態を作らない。**
ここは第4章との境界なので厳密に区別すること。

| | 内容 | 判定 |
|---|---|---|
| NG | `navigator.webdriver` を偽装する / UAを書き換える | **第4章で「やらないと決めた」こと** |
| OK | モニタ無しWindows機に**本当にデスクトップセッションと実ウィンドウを持たせる** | 偽装ではない。実際に画面がある状態を作るだけ |

モニタが無くてもデスクトップセッションが生きていれば実ウィンドウのChromeは動く。
現在の実証環境（実画面のmacOS）と同じ条件を作れるので、**ヘッドレス検知という論点自体が消える。**

**到達できなかった動画の代替を同じ界隈から選び直す**仕組みが要る（グリッドで集めたリンクをダンプして突き合わせる）。

原因は**取り残された chromedriver.exe が標準出力のファイル（e2e.out）のハンドルを握ったまま**で、`>>` の追記が

で親の死んだ chromedriver を PID 指定で止める、出力先は走行ごとに別名にする（`%TIME%` は1桁時に先頭スペースが入るので使わない）。
`--resume` は取得済みを正しく除外して続きから走る（実証済み）。

### ただし設計の結論だけ記録しておく（再検討不要）

コメントを載せる段になったら、以下で決まっている:

- **粒度を混ぜない**。動画（1行=1動画）とコメント（1行=1コメント）を別ファイルにする
- **縦持ち1本のCSVは禁止**。`TikUGC解析シート.xlsx` の `SUM(再生数)` が
  コメント件数ぶん重複加算され、**エラーが出ないまま約394倍になる**

- 返信は別テーブルにせず `parent_comment_id` で自己参照
- **19桁IDは必ず文字列で扱う**。`7284621209680022785` はExcelでダブルクリックすると
  `7284621209680020000` に化け、**警告なく結合キーが壊れる**
- CSV書き出し時のみ `= + - @` 前置文字をエスケープ（SQLiteには生のまま保存）
- **既存13列は順序ごと先頭に据え置く**（Excel貼り付け運用を壊さないため）

| `diag_dom.py` | コメント欄のDOM構造・スクロール可能な要素の特定 |
| `diag_listeners.py` | 要素が何のイベントを聞いているか（CDP `DOMDebugger.getEventListeners`） |
| `diag_wake.py` | 描画が動いているか（`requestAnimationFrame` のフレーム数） |
| `diag_dup.py` / `diag_smooth.py` | 重複要求の形・スクロール方式ごとの比較 |
| `diag_reply.py` / `diag_reply2.py` | 返信UIの探索とクリック結果 |

### 実行方法

> **重要: 1つのChromeインスタンスは1スクリプトが占有する。**
> 同じChrome（同じポート）に2つのスクリプトを同時接続させると互いに干渉して
> 結果が壊れる。実際にやらかした（取り直しの実行中に診断を走らせ、両方の結果を失った）。

#### 並行して作業する場合

**別プロファイル・別ポートなら独立して動かせる。** `--port` で接続先を選べる。

```bash
# 2つ目のChrome（別アカウント・別プロファイル）
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --user-data-dir="$HOME/.tiktok-ugc-profile-2" --profile-directory=Default \
  --remote-debugging-port=9223 --no-first-run --no-default-browser-check \
  --mute-audio "https://www.tiktok.com/" &

$PY spatest.py --port 9223 ...
```

**ただしIPアドレスは共有される。** 2セッションで同時に収集すると、TikTok側から見た
1IPあたりの要求レートは単純に足し算になる（現行設定なら約4回/分相当）。
収集を2本同時に回すなら `--calls-per-min` をそれぞれ半分にすること。

ログイン導線の確認程度（数ページの読み込み）なら、収集と並行させて問題ない。

```bash
# 1. ログイン済みChromeを起動（未起動なら。手動ログインが1回必要）
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --user-data-dir="$HOME/.tiktok-ugc-profile" --profile-directory=Default \
  --remote-debugging-port=9222 --no-first-run --no-default-browser-check \
  --mute-audio "https://www.tiktok.com/" &
```

**Chromeウィンドウを他のウィンドウで隠さないこと**（2-9）。
`spatest.py` は `Emulation.setFocusEmulationEnabled` で対策しているが、
起動時の `描画状態:` ログは毎回確認すること。

```bash
cd ~/tiktok-overnight
PY=/Users/belle/workspace/TikTok-ugc-analyzer/.venv/bin/python

# 2. 下見（動画を1本も開かない。指定リストに到達できるかも確認できる）
$PY spatest.py --music-url "https://www.tiktok.com/music/<楽曲>" --probe
$PY spatest.py --music-url "..." --probe --videos 対象リスト.csv

# 3. 本番（100本走行で実証済みの設定）
$PY spatest.py --music-url "https://www.tiktok.com/music/<楽曲>" \
  --videos 対象リスト.csv \
  --calls-per-min 4.0 --max-calls-per-min 6.0 \
  --interval 15 --jitter 0.5 --collect-scrolls 45 --resume \
  --out out.jsonl --log run.log --summary run_summary.json

# 4. 返信も取る場合
#    ↑に加えて --replies --reply-min 10 --reply-max 10
```

#### 主な引数

| 引数 | 既定 | 意味 |
|---|---|---|
| `--videos FILE` | なし | 対象動画のリスト。CSV/TSV/URL行から動画IDを拾う。**既存スクレイパーのCSVをそのまま渡せる**。指定が無ければグリッド順 |
| `--limit N` | 20 | **目標の総本数**（`--resume` 時は取得済みを差し引く） |
| `--resume` | off | 出力ファイルにある動画を飛ばす。途中で止まっても続きから走る |
| `--min-comments` / `--cap` | 20 / 300 | 上位リストが尽きるまで取る。前者が下限、後者が安全弁 |
| `--replies` | off | 返信も取る |
| `--reply-min` / `--reply-max` | 10 / 10 | 返信がこの件数以上のコメントだけ開き、1コメントこの件数まで |
| `--calls-per-min` / `--max-calls-per-min` | 1.8 / 2.0 | 平均と瞬間上限。**上げても2.5以上は無意味**（律速が別。第7章） |
| `--collect-scrolls` | 10 | 楽曲ページのスクロール回数。`--videos` 使用時は多め（45程度）にする |

#### 走行後に必ず確認すること

| 見るもの | 正常な値 |
|---|---|
| `描画状態:` | `visibility=visible` かつフレーム>0（2-9） |
| `対象動画の突き合わせ` | 「見つからない」が0本。あれば取れていない |
| `上位リストを取り切った` | 本数が対象数と一致 |
| `瞬間最大（60秒窓）` | 設定した上限以下 |
| **`aweme_id` の照合** | 出力の各コメントの `aweme_id` が行の `video_id` と一致（2-10） |

