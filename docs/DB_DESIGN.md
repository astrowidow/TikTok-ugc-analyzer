# データの持ち方 — 第1歩: 何を保存するか、何に縛られるか（2026-09-30）

## この文書の進め方

データの持ち方は、次の3歩で決める。**この文書は第1歩だけ。** 表の設計には、ここで合意してから入る。

1. **何を保存しなければならないか、どんな制約があるか**を洗い出す（この文書）
2. それをどうまとまりに分けるか（取り直せるもの／取り直せないもの、誰が作ったか、など）
3. 表やファイルの形

先に書いてしまった表の案は `docs/DB_TABLES_DRAFT.md` に退避した。第2・3歩の材料にするが、**まだ合意していないもの**として扱う。

数値は、シルエットの試験（880本、コメント取得27本）の実物を測ったもの。

## 1. 保存しなければならないもの（棚卸し）

最も大事な列は「**失ったら取り戻せるか**」。ここで保存の慎重さが決まる。

### 1-A. 外から取ってくるもの

| もの | 中身 | 大きさ（実測） | 失ったら取り戻せるか | 今どこにあるか |
|---|---|---|---|---|
| 動画一覧 | 楽曲ページに並んだ動画の URL と数値（既存 CSV の13列: Index, URL, 投稿日, 本文, いいね, 共有, コメント数, 再生, 保存, リポスト, 種別, 投稿者, 曲名） | 880本で約200KB | **取り戻せない。** 並びは推薦順で、時間とともに入れ替わる。9か月前の一覧には、今のグリッドに無い動画が多い | リポジトリ直下の `シルエット.csv` など（約90本の CSV が散在） |
| 動画の属性 | 投稿者のフォロワー数・bio・認証、投稿地域、言語、TikTok のカテゴリラベル、提案語、画面上の文字、エフェクト、広告フラグ、尺、音源など約40項目 | 880本で2.1MB | **取り戻せない。** 削除された動画は属性が取れなくなる（9か月で20%）。値はその時点のもの | `output/trial_silhouette/enriched.jsonl` |
| サムネイル画像 | 動画の表紙画像 | 634枚で141MB（1枚約220KB） | **取り戻せない。** 画像の URL が約24時間で失効するので、その場で保存するしかない | `output/trial_silhouette/covers/` |
| 投稿者の属性 | フォロワー数・動画数・総いいね・bio | 動画の属性に含まれている | **その時点の値しか取れない。** 投稿した時点のフォロワー数は取れない | 同上 |
| コメントと返信 | 1件あたり37項目＋投稿者情報32項目。本文・いいね数・返信数・投稿時刻・言語・「投稿者」印など | 27本で14MB（本体3,549件＋返信496件）。1本あたり約0.5MB | **取り直すのが高い。** ログイン済みの Windows 機で1本約3分、1回の取得は12時間まで。削除されれば取れない | `output/trial_silhouette/e2e/e2e.jsonl`、`output/ugc.db`（プロポーズ） |
| 取得の記録 | API を何回呼んだか、SPA 遷移したか、申告された総数と取れた数、所要時間、混入の有無 | 27本で1.4MB | **取り戻せない。** 後から「この取得は正しかったか」を判定する唯一の材料 | `e2e_summary.json`、`e2e.log` |

### 1-B. 手元で計算して作るもの

| もの | 例 | 失ったら取り戻せるか |
|---|---|---|
| 集計・サンプル | 週ごとの本数と再生数、離陸週、軸を考えるためのサンプル | **取り戻せる。** 1-A から同じ手順で作り直せる（抽出は乱数の種を固定している） |
| AI に渡す形に整えたもの | 圧縮した動画一覧、サムネの一覧画像（20枚で1枚）、動画ごとのコメント Markdown | **取り戻せる。** 4.5MB＋コメント Markdown 約0.5MB |

### 1-C. AI と人が作るもの

| もの | 例（シルエット） | 失ったら取り戻せるか |
|---|---|---|
| 分類の軸 | 界隈・フォーマット・動機の定義（`taxonomy.json`） | **同じものは作れない。** AI は毎回違う答えを出す。人が直した場合はその手間も消える |
| ラベル | 200本それぞれの界隈・確信度・根拠（`labels.tsv`） | 同上。作り直すと費用もかかる（1,000本で約10ドルの見込み） |

| 代表動画のリスト | 65本と、選んだ理由（`reps.tsv`） | 同上。人が確認・修正する工程 |
| コメント分析 | 動画ごとの反応の型と引用（`video_analysis.jsonl`）、界隈ごとの統合 | 同上 |
| レポートと原稿 | `REPORT.md`、note 用原稿、著者が書き足す箇所の一覧 | 同上 |
| **その成果物が何を見て作られたか** | 事前知識の申告、各担当の注記、どの入力を渡したか | **取り戻せない。** 「答えを見ていない」ことの証拠。後から証明する手段が他に無い |
| 人の考察（今後） | 「なぜバズったか」の章に人が書く内容 | **取り戻せない** |

## 2. 制約

### 2-A. 取得元（TikTok）から来る制約

| # | 制約 | 出所 | 保存への影響 |
|---|---|---|---|
| T1 | **失敗しても何も言わない。** 例外もエラーも出ないまま、データが1本ずれたり、20件で止まったりする | 引き継ぎ書 第0章 | 取れたデータと一緒に「取得の記録」（1-A）を残さないと、後から正しさを判定できない |
| T2 | 楽曲ページの並びは推薦順で、時間とともに入れ替わる | 7-D | 一覧は「その時点での見え方」でしかない。取得した日時と一緒に残す |
| T3 | 動画は削除される（9か月で20%） | 7-D | 属性は一覧取得と同時に取り、そのまま残す。後からは取れない |
| T4 | サムネの URL は約24時間で失効する | 7-D | 画像ファイルとして保存する |
| T5 | 写真投稿は属性が取れない | ToDo-1 | 「取れなかった」ことを記録する（欠損と区別する） |
| T6 | 再生数の推移も、投稿時点のフォロワー数も取れない | E2E_EVAL | 手に入るのは「取った時点の値」だけ。値には必ず取得日時を付ける |
| T7 | アカウントの @名 は変わる | COMPARISON（3件）、store の検算（8件） | @名 でアカウントを識別しない |
| T8 | ID は19桁 | 引き継ぎ書 第8章 | 数値として扱うと末尾が丸まり、結合が壊れる。常に文字列で持つ |
| T9 | コメントはログイン済みの実ブラウザでしか取れない。Windows 機で1本約3分、1回12時間まで | 7-C | 取り直しが高いので、取った分は全部残す |
| T10 | コメントは、一覧を取ったのと同じブラウザセッションでしか辿れない | 7-D | どのセッションで取ったかを記録する |
| T11 | 1件のコメントに、分析には要らない内部情報（`share_info` など）が大量に付いてくる。返信の一部は本体のデータの中に埋まって届く | 第8章 実装結果 | 分析用に整えるときに落とす列がある。生のデータを残すかどうかは判断が要る（第3章 Q2） |

### 2-B. 使う側から来る制約

| # | 制約 | 出所 | 保存への影響 |
|---|---|---|---|
| U1 | **Excel で開いて使う運用がある。** 既存13列は順序ごと先頭。19桁 ID は Excel で開くと丸まる。縦持ちにすると `SUM(再生数)` が約394倍になる。列数の上限は16,384 | 第8章 | 納品用の CSV は今の形を崩さない。保存の形と納品の形は別物として扱う |
| U2 | AI に一度に渡せる量に上限がある（コメント分析と執筆を別工程にしたのは、合わせると50万トークンを超えるため） | 第8章 | データは「AI に渡す分だけ」切り出せる形で持つ |
| U3 | **答えを見ない評価。** AI の各工程が何を見たかを後から証明できる必要がある | 第8章 | 成果物と一緒に、渡した入力と事前知識の申告を残す |
| U4 | 人がエディタで読む（Markdown） | E2E の運用 | レポートや AI への指示は、ファイルとして人が開ける場所に置く |
| U5 | 同じ動画・同じアカウントが複数の分析に出てくる（楽曲の分析とアカウントの分析の両方に入る動画など） | WORKFLOW_DESIGN 1.3 | ~~分析ごとにデータを複製すると、取得日の違う値が食い違う~~ → **制約ではなくなった**（第4章 Q5: 分析ごとに取り直し、重複と食い違いは受け入れる） |
| U6 | 媒体が増える（YouTube）。YouTube には無い値がある（投稿地域・提案語・保存数など） | WORKFLOW_DESIGN 1.4 | 「無い」と「取れなかった」を区別できる形にする |
| U7 | 利用者が複数になる（招待制） | ANALYSIS_PIPELINE 第8章 | 誰のデータか、誰の分析かを持つ必要がある。取ったデータを利用者間で共有してよいかは未定 |

### 2-C. 動かす環境から来る制約

| # | 制約 | 保存への影響 |
|---|---|---|
| E1 | **データが2台で生まれる。** 一覧・属性・分析は Mac、コメント取得と Web サービスは Windows 機 | 1か所に集める経路と、どちらを正にするかが要る。今は scp で手運び |
| E2 | Web サービスのジョブの状態はメモリ上にあり、再起動で消える | 12時間ジョブの途中経過をどこに残すか |
| E3 | 同じ Windows 機を別の作業（Web サービス）が使う。実際に、再起動の巻き添えで取得が途中で止まった | 取得は途中から再開できる必要がある（今の `--resume` と同じ） |
| E4 | リポジトリは公開。`output/` は git に入らない | データは git で守られない。バックアップは別に考える必要がある |
| E5 | 開発は1人＋AI。今の `store.py` は標準ライブラリだけで書いてある（pandas は空欄で整数列が小数になり、19桁 ID が壊れるので使わない） | 仕組みは単純に保つ。専用のサーバーを立てる DB は避ける |

## 3. 確認したいこと（回答は第4章）

第2歩に進む前に、ここを合わせたい。

| Q | 聞きたいこと | 私の考え |
|---|---|---|
| **Q1** | 第1章の棚卸しに**漏れはないか**。今後保存したくなりそうなものは何か。例えば動画本体や音声（GPU で音源の切り出し箇所を照合する案。大容量になる）、他の SNS の数値（Chartmetric など）、人の考察 | 動画本体は、保存するかどうかで容量が桁違いに変わるので、早めに知りたい |
| **Q2** | 取ってきた生のデータ（コメント1件69項目など）を**全部残すか**、分析に使う列だけ残すか | 全部残す。取り直せないうえ、後から「あの列を使いたい」が起きる（返信の埋め込みや「投稿者」印も、最初は落としていた列から見つかった）。1回の12時間ジョブで約125MB なので、置き場所に困らない |
| **Q3** | 2台のうち**どちらを正（原本の置き場）にするか** | Windows 機。取得も Web サービスもそこで動き、常時起動している。Mac は作業用の写しを持つ |
| **Q4** | データを**どれくらいの期間**残すか。バックアップは要るか | 取り直せないもの（1-A と 1-C）は消さない。バックアップは要る（今は無い） |
| **Q5** | 利用者が複数になったとき、**取ってきたデータ（動画・コメント）を利用者間で共有してよいか** | 今すぐは決めなくてよい。ただ、「誰の分析か」を持てる余地だけは最初から残しておく |

## 4. 決定（2026-09-30 ユーザー回答）

| Q | 決定 | ここから言えること |
|---|---|---|
| Q1 | **動画本体・音声は保存しない** | 一番大きいのはサムネイル（1枚約220KB）。容量は桁違いには増えない |
| Q2 | **取ってきたデータは全部残す** | 分析用に列を落とすのは「使うときに整える」側の仕事。原本は取ったままの形で残す（T11 の判断はこれで決着） |
| Q3 | **原本は Windows 機** | Mac で作ったもの（一覧・属性・AI と人の成果物）も Windows 機へ集める経路が要る（E1） |
| Q4 | **消さない** | バックアップ（E4）は別途。消さない前提なので、壊れたときの備えは要る |
| Q5 | **分析と分析は独立して扱う。** 分析 A と分析 B が同じ動画を参照しても、それぞれ別々に取得してよい。利用者からは、いつでも自分が初めて分析したように見える。それが一番単純 | 下記 |

### Q5 から言えること

- **保存の単位は「分析1回」になる。** 動画一覧・属性・サムネ・コメント・取得の記録・AI と人の成果物は、すべてどれか1つの分析に属する。分析をまたいで共有する「もの」の置き場は作らない
- **U5（同じ動画が複数の分析に出る）は制約ではなくなった。** 重複と、取得日の違いによる数値の食い違いは受け入れる
- 利用者間の共有の問題（U7 の後半）も消える。分析は誰か1人のもの
- 分析をまたいで**読むだけ**のワークフロー（比較・類推）は、それぞれの分析の成果物を読めば成り立つ。書き込みはしない
- 残る論点（第2歩で決める）:
  - **同じ分析の中で取り直す**（定点観測、到達できなかった代表の再取得）ときは、その分析の中に取得の記録が複数並ぶ。T2・T6 のとおり、値には取得日時が付く
  - 外部の知識（1-E の記事と知識ベース）は分析のデータではない。分析からは「どの版を見たか」だけを記録する

# 第2歩: 分析1回の中身をどう分けるか（2026-09-30、①〜⑤の分け方は合意済み）

## 5. E2E 試験のファイルを分けてみる

シルエットの E2E 試験を「分析1回」とみなし、`output/trial_silhouette/` と関連ファイルを全部、次の5つに振り分けた。

| 分類 | 意味 | 扱い |
|---|---|---|
| **① 原本** | TikTok から取ってきたもの、そのまま | 取り直せない。生のまま消さない（Q2・Q4） |
| **② 取得の記録** | ①をいつ・どう取ったか、うまく取れたか | 取り直せない。①と対で残す（T1: 失敗は無言なので、これが無いと①の正しさが分からない） |
| **③ 計算物** | ①から手元のスクリプトで作ったもの | 同じスクリプトで作り直せる。消えても困らない |
| **④ 成果物** | AI と人が作ったもの（＋それが何を見て作られたかの申告） | 同じものは二度と作れない。消さない |
| **⑤ 評価** | 成果物の出来を測ったもの | 試験のときだけ生まれる。運用の分析には通常ない |

| `e2e/ABLATION.md` ＋ `e2e/ablation/cap20` / `cap40` / `noreplies` | コメント量を変えて AI に分析し直させた出力と、その比較 |

### どれにも入れないもの

| ファイル | 理由 |
|---|---|
| `_contaminated/` | 答え（記事）を見た状態で作った第1回。無効な試験の残骸なので、残すが使わない。分類するなら「⑥ 無効」 |

### 分けてみて気づいたこと

1. **`reps.tsv`（代表リスト）は③と④の境目にある。** E2E ではスクリプトが機械的に選んだので③。しかし運用では人が確認して直す工程があり、直した時点で④になる。
   → 「スクリプトが出した案（③）」と「人が確定したもの（④）」を別ファイルにする
2. **②と④に穴がある。** 一覧取得のログと、使った指示書の版が残っていない。前者は取得の正しさ、後者は「答えを見ていない」ことの証明に要る
3. **原本がリポジトリ直下と分析フォルダに散っている。** `シルエット.csv` だけ場所が違う。分析1回の原本は、分析のフォルダに集める

## 6. 「同じ分析の中で取り直す」とは

同じ分析の中で、**同じ動画を2回以上取りに行く**こと。実は E2E ですでに3回起きている。

| 起きたこと | 1回目 | 2回目 |
|---|---|---|
| 動画の数値を2回見た | 2025-12-25 の一覧（`シルエット.csv`）で、ある動画の再生数は **573,200** | 2026-09-11 の属性取得で、同じ動画が **640,700** |
| コメント取得が途中で止まり、続きから再開した | 2026-09-12、9本目で止まった（別作業の巻き添え） | 同日、`--resume` で残りを取った |
| （今後ありうる）取れなかった動画を取りに行く | 代表65本のうち38本がグリッドに見つからず取れなかった | 後日、その38本だけもう一度試す |

つまり「分析1回 ＝ 取得1回」ではなく、**分析1回の中に取得が何回かある**。ここで決めたいのは次の2点だけ。

| 決めたいこと | 私の案 |
|---|---|
| 同じ動画の値が2つあるとき（573,200 と 640,700）、両方残すか | **両方残す。** 取得ごとに別ファイルにして、どちらも原本（Q2「全部残す」の延長）。分析でどちらを使ったかは成果物側に書く |
| 1か月後に同じ楽曲の一覧を取り直して、変化を見る（定点観測）のは、同じ分析か別の分析か | **別の分析（決定、ユーザー 2026-09-30）。** 変化を見たければ、2つの分析の成果物を読み比べる |

## 7. 外部の知識（決定）

記事や知識ベースは分析のデータにしない。**分析側には参照したものの URL（手元のファイルならパス）を一覧で残すだけ**にする（ユーザー、2026-09-30）。

## 8. コメントの原本の形（実データで確認、2026-09-30）

`e2e/e2e.jsonl` は **1行＝動画1本**。親子関係と動画との紐づけは JSON の中に全部残っている。

```
{ "video_id": "7532…250",                      ← どの動画か
  "comments": [                                  ← 本体コメント（135件）
      { "cid": "7565…264", "aweme_id": "7532…250", "reply_id": "0", "text": …, "digg_count": …,
        "reply_comment": [ … ] },                ← 本体に同梱されて届いた返信（主に投稿者の返信）
      … ],
  "reply_comments": [                            ← 「返信を表示」を押して取った返信（18件）
      { "cid": "7567…650", "aweme_id": "7532…250",
        "reply_id": "7565…264",                  ← 親の本体コメントの cid
        "reply_to_reply_id": "0" }, … ],         ← 返信への返信なら、その返信の cid
  "total": …, "has_more": …, "api_calls": …, …   ← 取得の自己申告
}
```

| 確かめたこと（27本） | 結果 |
|---|---|
| コメントの `aweme_id` が行の `video_id` と一致しない（別動画の混入） | 0件 / 4,045件 |
| 返信の `reply_id` が、同じ行の本体コメントに見つからない（親の無い返信） | 0件 / 496件 |
| 返信への返信（`reply_to_reply_id` ≠ 0） | 172件。親子は2段まで（`reply_id` は常に最上位の本体） |
| 本体に同梱された返信 | 143件（`reply_comments` とは別の場所にある。取り込むときに拾う必要がある） |
| コメントを取った27本が、属性の原本（`enriched.jsonl`）にもあるか | 27/27。`video_id` で結べる |

注意: **JSONL の中には「いつ取ったか」の絶対時刻が無い**（ファイルの更新時刻で代用している。第8章 実装結果 7）。②取得の記録に取得日時を必ず書く。

Excel 向けには、`store.py` が既にこれを平らな表（1行＝1コメント、`parent_comment_id` と `level` 列、本体の直後にその返信）に書き出せる。

## 9. 何で管理するか（提案、確認待ち）

| 置くもの | 形 | 理由 |
|---|---|---|
| **分析1回** | Windows 機の**フォルダ1つ**（`analyses/<analysis_id>/`）。中を ①原本 ②記録 ③計算物 ④成果物 ⑤評価 に分ける | 分析は独立（Q5）なので、フォルダを丸ごとコピーすればバックアップ・持ち出しになる |
| ①原本・②記録 | **取ったままのファイル**（JSONL・画像・ログ） | 全部残す（Q2）には、取った形のまま置くのが一番確実。TikTok は予告なく項目を増減させるので、先に表の形を決めると溢れた項目の置き場に困る |
| ③計算物 | ファイル。**分析ごとの SQLite（`store.py` の ugc.db 相当）もここに入る** | 数える・結ぶ・Excel に出すには SQL が便利。ただし原本から作り直せるので、壊れても消してよい |
| ④成果物・⑤評価 | ファイル（Markdown・JSON） | 人がエディタで読み、AI に渡す（U2・U4） |
| **サービス全体の台帳** | **SQLite 1本**（Windows 機） | 分析の一覧・誰の分析か・状態・ジョブの待ち行列。今はメモリ上にあって再起動で消える（E2）。中身は小さい |

つまり **SQL は「原本の置き場」ではなく「原本から作る検索用の写し」と「サービスの台帳」の2か所で使う**。
原本そのものを SQL に入れる案（今の `store.py` の考え方）と比べて、失うのは「原本を直接 SQL で引けること」だけで、写しを作れば同じことができる。
