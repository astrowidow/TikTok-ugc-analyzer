# 界隈の掘り下げ（完成後に、ある界隈の解像度を上げる）— 設計と作業記録（2026-10-06〜）

## 0. 一言で

レポートが完成したあと、利用者が「△△界隈のところが浅い（なぜバズったのかが弱い）」と言ったら、
**その界隈のコメントを約25分だけ取り足し、その界隈の分析をやり直して、レポート全体の整合を取りながら書き直す**。

ねらい: コメント取得の短縮（別のセッション。`docs/COMMENT_STRATEGY_HANDOVER.md`）で取る量を減らすと、レポートの大局は変わらないが、
小さな層の細部（例: きゃわの海外の地雷系・Jファッション層）を落とす。それを、利用者が気にした界隈だけ、あとから取り戻す。

## 2. 前提の数字（本番2曲、AI なしで数えた。2026-10-06）

| | シルエット（a20260930-2342-0035） | きゃわ（a20261004-0837-4e69） |
|---|---|---|
| 全動画 / ラベルあり / コメントあり | 911 / 286 / 192 | 1,716 / 229 / 159 |
| 界隈ごとの「ラベルあり・コメントなし」 | 0〜22本（再生10万以上 0〜15本） | 0〜13本（10万以上 0〜10本） |
| 界隈ごとの「続きを取れる動画」（上限40件で止まり、上位リストがまだ続く） | 1〜24本 | 0〜12本 |

- ラベルは全動画の一部だけに付く（層化のサンプル ∪ プール）。プールは必ずラベル対象に入るので、ラベル付きの約3分の2にはもうコメントがある
- 新しく取れる動画が0本の界隈（anime_fan・japan_interest・top_tiktoker）にも、続きを取れる動画は 1〜12本ある。
  逆に続きが0本の界隈（きゃわの ryosan_jirai・trend_girl）にも、新しく取れる動画（10万以上）が2本ずつある。2曲とも、どの界隈も何かしら取れる
- **大きな界隈は、取ったコメントの多くを読んでいない**（推定。personal_creator 2,206件のうち約23%、honke 6,418件のうち約12%）。
  今の界隈ごとのコメント分析は「1本あたりいいね上位8件の一覧＋全件は2〜4本」。小さな界隈はほぼ全部読んでいる。
  → 掘り下げでは、取り足すだけでなく、**読む量も増やす**（6 章の dcomments）
- 取れるのは楽曲ページのグリッドに出る動画だけ。本番2件は取得の直後なので全部見つかったが、グリッドは推薦順で入れ替わる（E2E で65本中38本が不到達）。
  完成から日が経つほど届かない動画が増える（推測）。届かなかった本数は利用者に伝える
- 取得の速さ（毎分3回の実走、`output/pacetest-20261005-3cpm/`）: 上限40件の動画は 40本で62分＝**1本約1.6分**。
  上限120件は、毎分2回の実走で40件の動画の約2倍（209秒／105秒）なので**約3.2分**（推測）。グリッドで対象を探すのに1〜2分（本番の記録）

## 3. 利用者の流れ

1. 利用者「〇〇のレポートの△△界隈のところ、なぜバズったのかが弱い。もっとコメントを取って掘り下げて」
2. AI が道具 `deepen`（界隈・利用者の言葉）を呼ぶ。アプリは取る動画を決めて待ち行列に入れ、こう返す:
   「△△界隈（dancer）で進めます。新しく8本・続きを3本取ります（約25分、14:30ごろ）。終わったら通知するので『〇〇の分析を続けて』と言ってください」
   - 確認で止めない（「この界隈・この本数で進めるね」と伝えて進める）。界隈の当て違いは利用者が言えば直せる
   - 取れる動画が無ければ、待たずに 6 章の仕事に入る（手元のコメントを深く読み直す）
3. Mac が取る → 通知「〇〇の取り足しが終わりました」
4. 利用者「続けて」→ AI が 6 章の仕事を片付ける → レポートが新しい版になる（前の版は history に残る）。何が変わったかを返す

**Q4（未決）**: 3→4 の「続けて」は、今の形（最初の分析の「続けて」と同じ）では要る。アプリから AI の会話を起こす手段が無く、
Claude デスクトップは道具1回が約60秒・1回の返答で道具は約20回まで（利用者の報告）なので、25分の取得を会話の中で待てない。
- A（今の作り）: 通知を見て「続けて」を1回
- B: 依頼した会話の中で待たせる（待つ道具を繰り返し呼ぶ）。Claude で収めるには取得を約15分以内にする必要（推測）。上限に当たれば結局「続けて」が要る。実機の確かめが要る
- どちらでも、取る動画の決め方と 6 章の仕事は同じ。変わるのは入口の待ち方と取得時間の目安だけ

## 4. 取る動画の決め方（`acquire/deepen.py` の `plan`）

1. 界隈 k の動画（`outputs/labels.tsv`）を2つに分ける
   - **新しく取る**: コメントが無い（`raw/comments.jsonl` に ok の行が無い）。属性が取れなかった（削除済み）・前に「動画が無い／コメントが無い」だった・前の掘り下げで取れなかった動画は外す。
     **再生の下限はその分析の週ごとの下限**（`min_plays_weekly`、既定10万。ユーザーの価値観「10万以下の動画の話は大局を見たいレポートではむしろ不適切」）
   - **続きを取る**: コメントはあるが、上限40件で止まり、まだ続きがある（`has_more` かつ取った件数がすべて上位リスト）。上限120件で取り直す（先頭から取り直すので前の分も含めて最大120件）。下限は掛けない（もう選ばれた動画）
2. 時間で配る: 目安25分から、決まった準備の分（Chrome・楽曲ページ・グリッドで探す。楽曲ページ1つにつき3分）を引き、
   **新しく取る動画を再生の多い順に**（1本1.6分）、残った時間で**続きを再生の多い順に**（1本3.2分）詰める
3. 楽曲ページが複数ある分析は、動画を見つけたページごとに分けて取る（本線と同じ）

数字（1本の分・準備の分・上限）は `acquire/deepen.py` の `EST` に置く（本線の `acquire/pipeline.py` の DEFAULTS は別のセッションが触るので使わない）。

## 5. 取る（取得の係とアプリ）

- 分析の `analysis.json` に `deepen`（今の回）を持つ: `round`・`status`（queued → running → done／failed）・`community`・`instruction`・`targets`・`est_min`・`result`。前の回は `deepen_history`
- **取得の係**（`acquire/worker.py`）は、待ち行列に「掘り下げの取得」も並べ、`acquire/deepen.py` の `Run` で取る。本線と同じロック・同じ速さ・同じ Chrome
  - spatest に渡すのは pool.tsv の形（video_id・seq・cap・priority・reasons）。**差し替えはしない**（候補を渡さない。界隈の外の動画になるため）
  - 取った行は別のファイル（`raw/deepen/r<回>.jsonl`）に書き、終わったら原本（`raw/comments.jsonl`）に足す。続きを取った動画は、前のコメントと cid で合わせる（取り直しで減ったら足さない）。
    そのあと `analysis/prep_comments.py` で `derived/comments` を作り直す（本線の comments_md と同じ引数。プールの理由は掘り下げの印を足した写しを渡す）
  - 止まったら（ブロック・ログイン切れ以外の例外）、取れた分だけ足して終える。待って取り直すことはしない（短い仕事なので）
  - 打ち切り: 目安＋10分
- **アプリ**（`collector/collector_app/app.py`）: 掘り下げの取得の間も眠らせない・Chrome を開き直す・メニューに状態を出す・終わったら通知

## 6. AI の仕事（「続けて」のあと。`flow_w1.py`）

道具 `deepen` を受け付けたとき、仕事の列の末尾に足す（完成後の直し revise と同じやり方）:

| # | 仕事 | 中身 |
|---|---|---|
| 1 | **dcomments**（AI） | 界隈 k のコメント分析をやり直す。材料を増やす（1本あたりいいね上位 8 → **15件**、全件を読む動画 2〜4本 → **6〜8本**。今回取り足した動画に印）。前回のまとめと利用者の言葉を渡し、そこを狙って読む。出力は今の形＋`#### 前回からの変化` |
| 2 | **outline_revise**（AI） | 構成案（記事全体の主張と章ごとの主張・根拠）のうち、この界隈に関わる章を直す。全体の主張が変わるかを判断し、書き直す章と理由を決める（全体の主張が変わったら冒頭も） |
| 3 | write×（AI） | 2 で決めた章を書き直す（前の原稿を読んで、この界隈に関わらない部分はなるべく残す。文体は前の原稿に合わせる） |
| 4 | **review**（AI） | 全章を通して読み、直した界隈の話とほかの章（分岐点・結果・冒頭の「先に結論」など）のずれを探す。ずれがあれば、その章の直しを足す（1回だけ） |
| 5 | write×（AI） | 4 で見つかったずれの直し |
| 6 | finish×（AI） | 直した章だけ note 用に仕上げ直す |
| 7 | finish_title（AI） | 全体の主張が変わったときだけ |
| 8 | assemble → verify → export（サービス）→ done | 組み立て・検算・Excel 用 ZIP（取り足したコメントを含む）・完了の知らせ（取り足した本数・件数、直した章、構成案の変更の一言） |

- 1 の dcomments が書く `outputs/synthesis/<k>.md` は前の版を `outputs/synthesis/history/` に残す。章・構成案も同じ（`chapters/history/`・`outline_history/`）
- 界隈の分け方（ラベル）は変えない。界隈の中に別の動機の層が見つかったら、その界隈の節の中で層として書く
- 分析の独立: 使うのはその分析のデータだけ

## 7. 道具（`mcp_proto.py`）

community は界隈のキーか、レポートでの呼び名（アプリが界隈の一覧から当てる。当たらなければ一覧を返す）。instruction は利用者の言葉そのまま。
