# 同じ曲のファンの音源も取る — 設計と作業記録（2026-10-06、0.6.7〜0.6.8）

## 0. 一言で

取得のはじめに、**同じ曲をファンが上げた音源（「オリジナル楽曲 - 〇〇」。曲の別の部分の切り抜きなど）を探し、よく使われていれば合わせて取る**。
あわせて、AI に「どの投稿がどの音源か」と音源ごとの内訳を渡し、音源ごとに使われ方が違えば書く（違わなければ触れない）ように指示書を直した。

## 1. きっかけ（きゃわの見落とし）

- ユーザー（10/6）「きゃわぽっぴんどぅーは自己紹介の文脈で使われたのが大きいのに、分析に一切入っていない。歌詞の『血液型とかなんだとか』に合わせて自分の血液型を言うような。大局を見るうえで大きな見落とし」
- 自己紹介の波の起点は若葉のあさん（@ilife__wakaba、6/23）の「血液型とMBTIみんなもおどってみてね」。2番の「血液型とかMBTIとかなんだとか」のところ。
  著者の月報（2026.7版）も「別パートが UGC として発生。血液型や MBTI など自己紹介フォーマットとして使われている」と書いている
- この波は、ファンが上げた12秒の音源「オリジナル楽曲 - 쿠레아.⋆𝜗𝜚」（7643306519803906823、**39K**）に乗っていた。
  取ったのは公式の2つ（31.1K・17.7K）だけ。受け付けで楽曲ページを選ぶとき、題と作者が曲名・アーティスト名に合わない音源（個人の音源）を外していたため（`proto_runner._music_fits`）。
  曲全体の UGC の約4割を見ていなかった
- 集めた 1,711本にも手掛かりは少しあった（涼森れむさん 53万再生「みんなの血液型とMBTIも教えてー！」、2番を踊った人の説明文、検索候補「血液型とかなんだとか」）が、AI は波として拾わなかった

## 2. 同じ曲かの見分け方

動画のデータ（itemStruct）の `music.tt2dsp.tt_to_dsp_song_infos[].MetaSongId` は、TikTok がその音源を照合した曲の番号。
**公式の音源も、ファンが上げた「オリジナル楽曲 - 〇〇」も、同じ曲なら同じ番号**になる（きゃわ: 公式2つとファンの音源がどれも 7644122555377502225。Apple Music の SongId 6773196371 も同じ）。
ログインなしの動画のページで読める。番号の無い音源は、同じ曲か分からないので取らない。

## 3. 見つけ方（`acquire/pipeline.py` の `search_fan_sounds`・`Run.add_fan_sounds`。取得の段の最初の `resolve`）

1. 曲名の discover のページ（ログインなし）の人気の動画16本の音源を読む。取るページ（公式）の音源を使った動画から曲の番号を知る
2. 読んだ動画の関連する検索の語（suggestedWords）とハッシュタグから、**曲名の表記ゆれ・曲名を含む語**を多い順に3つ選び、その discover のページも同じように読む。
   表記ゆれは、かな・カタカナ・濁点と半濁点・伸ばし棒・記号の違いを見ない鍵（`kana_key`）で見分ける
   - きゃわ: 39K の音源は曲名のページには出ず、「キャワポッピンドゥー」「きゃわほっぴんどぅ」「きゃわぽっぴんどぅー ダンス」のページに出た（ハッシュタグのページはログインなしだとエラーで使えない）
3. 曲の番号が同じで、取るページでない音源を、全部開いて UGC 数を読む
4. **主のページの UGC の2割以上**（公式の別版と同じ基準）を**全部**、大きい順に足す（音源A・B・C の並びになる）。足したページは `raw/music_pages.json` に `kind: "fan"`（音源の長さつき）、
   分析の目録に `fan_music_urls`。探した記録は `raw/sound_search.json`
   - 0.6.7 では時間を理由に「大きい順に1つ」にしていたが、ユーザー「こういう変な制限はしなくていいよ」で 0.6.8 から数の上限なし（UGC 数を読む数の上限も外した）
   - 1つ足すと動画が約850本増え、属性を取るだけで約50分延びる。きゃわなら3つ（39K・8.5K・6.9K）足すので、取得は約3時間延びる見込み（推測）
5. 曲の公開の時刻（それより前の投稿を除く）は、ファンの音源を除いた公式のページで決める（`Run.release_urls`）

探さないとき: 利用者が楽曲ページの URL を渡した分析（`start_analysis` の `music_urls`。設定 `fan_sounds: 0`）、試験（`UGC_COLLECTOR_NO_INSPECT`）。
探す途中で失敗しても取得は止めず、受け付けで決めたページで進める。

## 4. AI に渡すもの・指示書

- `analysis/build_llm_input.py`: 音源が2つ以上なら、動画ごとに `sound`（A・B・C…。ページの順。動画の音源の id で当て、読めなければ見つけたページで）と、
  音源ごとの要約 `llm_input/sounds.json`（題・作者・ファンの音源か・長さ・UGC 数）。ラベル付けの入力は「元音源=True」の代わりに「音源=C」
- `flow_w1.py`: 動画の1行（vline）に「音源C」。共通の材料・段階の材料に「音源ごと」（UGC・集めた本数・最初の投稿・本数のピーク週・再生の最多）、
  曲の章の材料には画面の文字と提案語の上位も。UGC の内訳はファンの音源と分かる書き方に
- 指示書（ユーザー「別の使われ方が起きていない時にいちいち『起きていませんでした』とレポートに書いてほしくはない」）
  - `service_prompts/w1/phases.md`: 音源ごとに担い手・使い方・時期が違えば、段階の区切りと経路の下書きに書く。違いが無ければ触れない
  - `service_prompts/w1/outline.md`: 別の部分の音源で新しい使い方の波が起きていれば、主張と経路・分岐点・切り出し箇所の章に割り振る（なぜその部分がその使い方に向いたかまで）。
    違いが無ければどの章でも触れない（「別の使われ方は無かった」とも書かない）
  - 分岐点の章の例に「曲の別の部分を切り抜いた音源で新しい使い方が始まった瞬間」、切り出し箇所の章に「音源ごとに曲のどこで・どう使われたか」

## 5. 残っていること

- 切り出し箇所の歌詞を音から直接つかむ（音源の音声を文字にして歌詞と突き合わせる）は、ユーザー「いったんいいや」。音源が取れていればコメントから経路をたどれる見込み
- きゃわを 0.6.7 で取り直して、自己紹介の波がレポートに出るかはまだ確かめていない
- 知識ベースの用語集に「同一曲が別パートで自己紹介フォーマット化（きゃわぽっぴんどぅー）」が入っていた（答えの混入。AI は読んでいたが拾わなかった）
