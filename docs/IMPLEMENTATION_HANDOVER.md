## 1. 決まっていること（覆さない）

### 1-1. 方式（BLUEPRINT）

- **2回着席**: 利用者は自分の AI に「〇〇を分析して」（1回目）→ 取得完了のメールのあと「続けて」と言い、界隈の案に答える（2回目）。それで完了
- **取得を全部先に済ませる**: 一覧 → 属性 → **AI を使わない数字と属性の規則で候補プールを決めてコメントを取る**。AI の出番は2回目の着席の1区間だけ
- **AI は待たない・見に来ない**: ポーリング、定期実行、ルーティン、GitHub 連携は使わない。待ち中に利用枠を使わない
- **型はサービスが持つ**: 手順・指示書・検算・状態はサービス。AI は「次の仕事を聞く → やる → 返す」の実行係
- **人の確認は H1（界隈の確認）だけ、会話の中で答える。** H2（段階）・H3（代表）・H4（考察）は置かない。考察と直しは完成後の H5
- 代表の選定はセル（界隈×段階）でやる。ただし**プールの中から、数字で**選ぶ（AI も人も使わない）

### 1-2. 利用者から見た形（2026-09-30 確定）

- **利用者が触るのは自分の AI アプリ（Claude か ChatGPT）だけ。Web サービスを意識しない**
- 接続: アプリの**コネクタ**機能に、サービスを**最初に1回だけ登録**する（運営が横で一緒に）。試作は**利用者ごとの秘密の URL**。
  将来必要なら OAuth（登録時に1回だけブラウザでサービスにログイン）。**プラグインは使わない**
- 定型の指示（繰り返し方・指示書）は、サービスが**接続を通して**渡す（`next_task` が毎回指示書を返す）
- 進み具合は会話で聞く（`status`）。取得の完了はメール。**成果物は、AI とメールが出すダウンロードのリンク**（クリックするとファイルが落ちるだけ）
- **指示の編集は会話で。保存先はサービス（利用者ごと）**:
  - 変えてよい4項目: **文体**／**レポートの重点**／**界隈の分け方の方針**／**コメント分析の観点**。空欄ならデフォルト（こちらで設定）
  - 変えられない部分: 出力の形、検算、仕事の刻み方、繰り返し方
  - 設定の道具は、利用者が頼んだときだけ AI が使う（＝設定の奥に隠す）
  - 「今後ずっと」（設定）と「この分析のレポートだけ」（H5 の直し）は、利用者の言い方で分ける
  - 分析ごとに、使った設定と指示書の版を記録する
- **利用者向けの Web 画面は作らない**（E2E_TODO の E1〜E4 は会話とリンクに置き換え）。Web 画面は運営用と予備。**既存の CSV 出力機能はそのまま残す**（本番で使われている）

### 1-3. データと運用（2026-09-14〜30 のユーザーの決定）

- 分析どうしは独立。同じ動画でも分析ごとに取り直す。共有の動画台帳は作らない
- 取ったデータは全部、取ったままの形で残す。消さない。動画・音声ファイルは保存しない
- 正（原本の置き場）は Windows 機。1分析＝1フォルダ。SQLite は「原本から作る検索用の写し」と「サービスの台帳」だけ
- 外部の知識（記事など）は参照先の一覧として残すだけ
- 利用者は友達3人（IT に詳しくないマーケター）。Claude と ChatGPT の**両対応は必須**
- **API は使わない**（利用者は一般の定額プラン）。サービスは利用者の AI のログイン情報を持たない
- 知識ベースは本番では全記事を含める。対象楽曲に触れる記事を除くのは記事と比べる試験のときだけ
- 今回は運営の TikTok 捨てアカウント1つを全員で使い、取得は直列。利用者ごとのアカウントは疎通の次のタスク

### 1-4. プラン（2026-09-30 調べ、BLUEPRINT 第7-1節）

## 4. 段1: 試作の接続口

### 4-1. 置き場所と載せ方

- 本番の Web サービス（FastAPI、`main.py`）に MCP サーバーを**載せる**。別プロセス・別ポートにしない（ngrok の公開 URL が1つしかないため）
- 新しいモジュール（例: `mcp_proto.py`）に接続口を書き、`main.py` の変更は「取り込んでマウントする数行」と「Basic 認証の除外」だけにする
- **接続口の読み込みに失敗しても既存の Web サービスを落とさない。** `start.bat` は pip が失敗しても既存のパッケージで起動を続ける作りなので、
  `mcp` が入っていないと `import` で落ちて本番が止まる。`try/except ImportError` でマウントを飛ばし、ログに警告を出す
- `requirements.txt` に `mcp`（公式の Python SDK）を足す。Streamable HTTP で出す。既存の FastAPI への載せ方（マウント、lifespan でセッション管理を走らせる）は
  **入れた版の SDK の README で確かめてから書く**（版で書き方が変わっている）
- 触る前に: 本番の `main.py`・`scraper.py`・`requirements.txt`・`start.bat` を Mac に写して、リポジトリの版と diff を取る。**違っていたら本番の版を土台にする**。
  本番のファイルは `*.bak-20261001` のように日付つきで控えを残す
- 再起動: Web サービスの python（コマンドラインに本番フォルダの `main.py`）・その cmd・ngrok を PID で止めて `schtasks /Run /TN tiktok-ugc-web`。
  **取得の python（`tiktok-overnight` や `tiktok-e2e`）と Chrome（9222）には触らない**
- 再起動の後に確かめる: 公開 URL の `/` が Basic 認証つきで 200、なしで 401。既存の `/api/*` が今までどおり応答する

### 4-2. 認証と URL

- Claude のカスタムコネクタは「URL（＋任意で OAuth）」しか渡せず、任意のヘッダーを付けられない。Basic 認証は使えない
- 試作は**利用者ごとの秘密の URL**: `https://giblet-squishy-icing.ngrok-free.dev/mcp/<秘密の文字列>`（32文字以上の乱数）
- 秘密の文字列 → 利用者 の対応は、Windows 機の**リポジトリ外・`output\` 外**のファイル（例: `C:\Users\astrowidow\ugc-secrets\mcp_users.json`）に置く。知らない文字列には 404、ログに記録
- Basic 認証の除外は `/mcp/` で始まるパス（と段3の `/dl/`）だけ
- 試作で発行するのは運営（ユーザー本人）の1つだけ。その URL は Mac の `~/.tiktok-ugc-win-credentials` に追記する（URL 自体は文書・作業記録に書かない）
- 秘密の URL が漏れても届くのはその利用者の分析だけで、TikTok や Windows には届かない作りにする（試作の道具は分析フォルダを読む・書くだけ）
- ngrok の無料枠: ブラウザ向けの警告ページが MCP の通信に挟まらないか、転送量・リクエスト数の上限を確かめる。挟まるなら回避策を調べてから T1 の手順書を出す

### 4-3. 道具（試作は4つ）

| 道具 | 入力 | 返すもの |
|---|---|---|
| `status` | （任意）分析 ID | その利用者の分析の一覧と状態（取得中なら残り時間、AI の番、確認待ち、完了）。日本語の短い文＋機械用の欄 |
| `next_task` | 分析 ID | 次の仕事1つ: `task_id`、`kind`、題名、**指示書（Markdown）**、入力（短いものは本文に、長いものは `read` で取る目録）、出力の形、進み具合（例「3/13」） |
| `submit` | `task_id`、出力 | 検査して取り込む。良ければ `{ok: true, 進み具合, 次は next_task を呼ぶ}`、だめなら `{ok: false, 理由の一覧}`（同じ `task_id` で出し直させる） |
| `read` | 分析 ID、何を（名前）、ページ | 仕事に要る資料: サムネのシート画像（MCP の画像として返す）、動画1本のコメント、長い表の1ページ |

`kind` は4種類: `ai`（やって `submit`）／`ask_user`（**利用者に見せて答えを待ち**、答えを `submit`）／`wait`（取得中。残り時間を伝えて止まる。段2から）／`done`（完了。成果物を伝えて止まる）。

### 4-4. 「繰り返し方」を AI に渡す（プラグインなしで回すための肝）

AI に渡す定型は短く、**3か所に同じことを書く**: MCP の初期化で返す `instructions`、各道具の説明文、`next_task` の返り値の末尾。

> 利用者が「〇〇の分析を続けて」と言ったら、`next_task` を呼び、返ってきた指示書どおりに作業して `submit` する。`kind` が `done` か `wait` になるまで、利用者に確認せずに繰り返す。
> `kind` が `ask_user` のときだけ、その内容を利用者に見せて答えを待つ。`submit` が差し戻されたら、理由を読んで直して出し直す。
> 途中経過や入力の中身を会話に書き写さない（利用枠を節約するため）。

出力は TSV か JSON の最小限。入力を会話に写させない。

### 4-5. 仕事の状態（どこで止まっても続きから）

- 仕事の状態は分析フォルダの中にファイルで持つ（例: `state/tasks.jsonl`）。`pending → issued（渡した時刻）→ done`
- `next_task` は、まだ done でない最初の仕事を返す。**`issued` のまま30分返ってこない仕事は渡し直す**（AI が落ちた・枠に当たった）。D7（枠に当たったら続きから）もこれで済む
- done の仕事に `submit` が来たら「受領済み」と返して何もしない
- 前の仕事の結果を使う仕事（ラベルは確定した軸を使う）は、**渡す時点で**前の結果を読んで指示書に差し込む
- 仕事ごとに「渡した文字数・受け取った文字数・かかった時間・差し戻し回数」をログに残す（T3 の見積りと、仕事の刻み方の調整に使う）
- 1回の道具の結果は**2万トークン程度まで**を目安に切る（`taxonomy_sample.md` は14万バイトあるので `read` のページで4〜5回に分ける）

- 利用者向けの Web 画面を作る（運営用の最小限の確認画面は可）
- Bot 判定の回避（COMMENT_ACQUISITION_HANDOVER 第4章）
- python の名前指定の kill／取得の走行中に Chrome（9222）や TikTok アカウントに触る
- 秘密の文字列をリポジトリ・文書・作業記録に書く／コミット・push
- H2・H3・H4 を作る／段4・5に入る
