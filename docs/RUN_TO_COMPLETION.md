# 分析を最後まで走り切らせるための調査（2026-09-30）

> **2026-10-06 追記**: Claude デスクトップの Code タブ（中身は Claude Code）なら、裏で走らせたコマンドが終わると Claude を起こし直す仕組みで、
> 取得を待ってから完成まで一気に回せる見込み。案と確かめることは `docs/CODE_TAB_ONE_SITTING.md`。

目的: 利用者が「分析して」と言ったら、界隈分類の確認（H1）以外は止まらずに最後まで進むこと。
障害は2つ: **①取得の待ち**（一覧・属性で約1.5時間、コメントで数時間〜12時間）と **②定額プランの利用枠**。
前提: API は使わない。利用者は一般の Claude（Pro/Max）か ChatGPT（Plus/Pro）の利用者。両対応は必須。
AI は利用者のアプリ上でプラグインとして動き、手順と指示書はサービスが持つ（`docs/AI_ACCESS_UX.md` 第7章）。

調べたのは各社の公式の説明だけで、**実機ではまだ試していない**。書いてあることと推測は分けて書く。

---

## 1. 結論

1. **AI に待たせない。** 1つの会話の中で何時間も待つ方式は、公式の説明を見る限り当てにできない（Claude のクラウドのセッションは「しばらく動きがないと止まり、裏で動いていた処理は戻らない」と明記されている）。
   AI の作業は「取得が終わってから始まる区間」に分け、**区間ごとに AI を起こし直す**。
2. **起こし方は、両社とも「定期実行」を基本にする。** 利用者の AI に定期実行のタスクを1つ作っておき、AI が決まった間隔でサービスに仕事を見に来る。
   - Claude: Cowork の定期実行（最短1時間おき、クラウドで動くので PC は閉じていてよい、プラグインと接続を使える）
   - ChatGPT: 定期実行（分単位の間隔が可、プラグインと接続を使える）
   - 加えて、Claude は「ルーティン」の起動 URL でサービスから即座に起こせる。ただし利用者の GitHub アカウントの連携が要る
3. **利用枠は「どこで止まっても続きから」で吸収する。** 状態はすべてサービスが持ち、AI の1回の実行は「次の仕事を片付けられるだけ片付けて終わる」だけにする。
   枠に当たって途中で止まっても、枠が戻った後の次の定期実行が続きを拾う。**利用者は何もしなくてよい**。
   代わりに、枠の小さいプランでは**分析が何日かに分かれる**。1回の分析でどれだけ枠を使うかは、公式に数字が無いので実測が要る。
4. この形なら、公式の説明の範囲で**2つの障害はどちらも設計で吸収できる**。
   残る不確実性は第5章の5点で、どれも実機で1回試せば分かる。

### 2-2. 設計の結論

**AI の作業を、取得の後ろで3つの区間に分ける。** 区間の間は AI は動かず、サービスだけが動く。

```
利用者「分析して」
 └ AI: サービスに分析の開始を頼む（すぐ終わる）
      サービス: 一覧・属性・サムネを取る（約1.5時間）
 ─── 起こす ───
 区間1  AI: 界隈の軸の案 → 利用者に確認（★H1。ここだけ人を待つ）
 ─── 利用者が答える（会話の中）───
 区間2  AI: ラベル付け → 段階 → 代表の確定をサービスに渡す
      サービス: コメントを取る（数時間〜12時間）
 ─── 起こす ───
 区間3  AI: コメント分析（動画1本ずつ）→ 執筆（章ごと）→ 仕上げ → 完了
```

**「起こす」の手段**（上から順に採る）:

| 手段 | Claude | ChatGPT | 待ち時間 | 利用者の手間 |
|---|---|---|---|---|
| A. 定期実行が見に来る | Cowork の定期実行（1時間おき） | 定期実行（例: 15分おき） | 最大で間隔ぶん | 最初に1回、タスクを作る（AI に頼めば作れる） |
| B. サービスが起こす | ルーティンの起動 URL | Gmail 起動（サービスが利用者にメールを送る） | ほぼ無し | Claude は GitHub 連携とルーティンの作成、ChatGPT は Gmail の接続 |
| C. 利用者が「続けて」と言う | 取得完了のメールを見て打つ | 同左 | 利用者次第 | 毎回 |

A を基本にし、B は「待ちを縮めたい人向けの追加」、C は A・B が駄目だったときの逃げ道にする。
A の待ちは区間の数（2回）× 間隔なので、Claude でも最大2時間ほどしか増えない。全体が1〜2日かかる分析なので、実用上は問題にならない。

### 2-3. 待っている間に枠を使うか（2026-09-30 追記。ユーザーの指摘）

- **待っている間、AI は動いていないので枠を使わない。** 取得の間に動いているのはサービス（Windows 機）だけ
- 枠を使うのは、**定期実行で AI が起きて「仕事はあるか」を見に来る1回ごと**。仕事が無ければすぐ終わるので1回は小さいが、ゼロではない（起動時の指示の読み込みと、道具の呼び出し1回分）
- 見に来る回数を減らす手段（上から順に）:
  1. **サービスから起こす**（Claude のルーティン、ChatGPT の Gmail 起動）: 見に来る回数はゼロ。仕事が出来たときだけ起きる
  2. **起きる時刻を1回だけ予約する**: サービスは取得の終わる時刻をほぼ正確に見積もれる（属性は1本約3.2秒、コメントは1本約3分）。取得を頼んだときに AI が「終わる予定時刻の少し後に1回だけ起きる」予約を作る。外れたら次の予約をもう1回。1回の待ちで見に来るのは1〜2回で済む。**Claude の Cowork の定期実行に「1回だけ」の予約があるかは説明に見当たらない**（ルーティンと、PC 上の Code タブの定期実行にはある）。ChatGPT は定期実行の繰り返し規則を編集できるが、1回だけの予約ができるかは要確認
  3. 定期実行（1時間おき・15分おき）: 分析が待ちの間だけ作り、終わったら消す。常時は置かない
- 実機確認 R5 で、見に来る1回あたりの枠の消費も測る

## 3. 障害②: 利用枠

### 3-1. 調べて分かったこと

| | 公式の説明にあること | 出典 |
|---|---|---|
| Claude の枠の仕組み | **5時間ごとに戻る枠**と**週ごとの枠**がある。claude.ai・Claude Code・デスクトップ（Cowork を含む）で**同じ枠を共有**する。使う量は会話の長さ・機能・モデル・effort で変わる | [使用量の仕組み](https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work)、[Pro/Max で Claude Code](https://support.claude.com/en/articles/11145838-use-claude-code-with-your-pro-or-max-plan) |
| Claude の枠の量 | **具体的な数字は公開されていない** | 同上 |
| Claude で枠に当たったら | 「戻るのを待つ、プランを上げる、追加利用分を買う」のどれか。**途中の作業が自動で再開するとは書かれていない**。ルーティンは「枠を超えると、戻るまで新しい実行は断られる」 | 同上、[ルーティンの使用量](https://code.claude.com/docs/en/routines#usage-and-limits) |
| ChatGPT（Codex）の枠の量 | Plus は5時間あたりの目安がモデル別に公開されている（例: GPT-6.1 Sol で 15〜160 メッセージ、GPT-6 Luna で 350〜3,000）。週の枠もある。**Pro には5時間の枠が無い** | [Codex の料金と枠](https://learn.chatgpt.com/docs/pricing) |
| ChatGPT で枠に当たったら | 「**進行中の1回分は、枠に当たってもそのまま最後まで続けられる**（公正利用の範囲で）」。その後は待つか、追加分を買う | 同上 |

### 3-2. 設計の結論

1. **どこで止まっても続きから**: サービスが「どの仕事が済んだか」を全部持つ。AI の1回の実行は「次の仕事を取る → 片付ける → 返す」を繰り返し、止まったら止まったところまでが残る。枠が戻った後の定期実行（第2章の A）が、次の仕事から続ける。**利用者の操作は要らない**
2. **仕事を小さく切る**: 1つの仕事は、動画1本のコメント分析や章1つの執筆くらいの大きさにする。途中で止まっても失うのは最大で仕事1つ分
3. **枠を食いにくくする**:
   - 量の多い仕事（ラベル付け・コメント分析）は、軽いモデルでも品質が落ちないかを確かめ、落ちなければ軽いモデルを指定する（Claude はプラグインのサブエージェントでモデルを指定できる）
   - コメントは標準40件に絞る（決定済み）
   - 知識ベース（約10万字）は執筆の仕事にだけ渡す
4. **利用者に伝えること**: 分析1回が枠をどれだけ使うか、プランごとに何日かかるかを、実測してから利用者に示す。週の枠を分析で使い切ると、利用者がふだん使う分に響くことも伝える

## 4. 利用者から見た流れ（この設計で）

| いつ | 利用者 | 裏で起きていること |
|---|---|---|
| 最初の1回 | アプリにログインし、プラグインを入れ、「UGC 分析を使えるようにして」と言う | AI が定期実行のタスクを自分で作る（作れるかは第5章で確認） |
| 開始 | 「シルエットを分析して」 | サービスが取得を始める |
| 1〜3時間後 | 通知を見て、界隈の案に答える | 定期実行で AI が起き、軸の案を出して利用者を待つ |
| 以後 | 何もしない | 区間2 → コメント取得 → 区間3。枠に当たれば止まり、戻った後の定期実行で再開 |
| 半日〜数日後 | レポートを読む。直したければ言う | 完了 |

## 5. 実機で確かめること（ここを通れば「確実」と言える）

| # | 確かめること | 手順 | 分かれ目 |
|---|---|---|---|
| R1 | Cowork の定期実行から、自作の接続（サービスの道具）を**承認なしで**呼べるか | 道具2つだけの試作の接続口と、仕事を1つ用意し、Cowork に1時間おきのタスクを作って放置する | 呼べなければ、Claude は B（ルーティン）か C に寄る |
| R2 | 会話で頼んで、AI が**自分で定期実行を作れるか**（Claude Cowork・ChatGPT） | 「UGC 分析を使えるようにして」とだけ言う | 作れなければ、最初の設定の手順が1つ増える |
| R3 | ChatGPT の定期実行から、利用者が足した接続（開発者モード）を使えるか。Plus で分単位の定期実行を作れるか | R1 と同じことを ChatGPT で | **使えなければ ChatGPT 対応は C（毎回「続けて」）になる。両対応の成否はここ** |
| R4 | 枠に当たって止まった後、次の定期実行が本当に続きを拾うか | わざと大きめの仕事を流して枠に当てる | 拾わなければ、サービス側で再試行の仕組みを足す |
| R5 | 分析1回（シルエットの E2E 規模）で、Claude Pro・ChatGPT Plus の枠をどれだけ使うか、何回の実行に分かれるか | E2E の入力を試作の接続口から流す | 利用者に伝える所要日数と、推奨プラン |

R1・R2・R4・R5（Claude）は運営の Claude アカウントで、R2〜R5（ChatGPT）は ChatGPT の有料アカウントで行う。
Claude のルーティン（B）を試す場合は、運営の GitHub アカウントの連携も要る。
