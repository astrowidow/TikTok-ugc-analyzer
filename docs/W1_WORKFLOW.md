# W1: TikTok 楽曲バズ分析の手順（2026-09-30）

楽曲を1曲指定してから、レポートを納品するまでの全手順。E2E 試験（シルエット、2026-09-12〜14）で実際に通した手順に、
その後の決定（コメント量、確認工程、分析フォルダ）を足したもの。新しい下回りでは、この1行1行が Step になる。

凡例:

- **誰が**: コード／AI／人。AI は利用者自身の Claude・ChatGPT（第4章）
- **どこで**: Win＝Windows 機（取得と Web サービス）／AI＝利用者の AI／人＝利用者の手元
- **置き場**: 分析フォルダの ①原本 ②取得の記録 ③計算物 ④成果物 ⑤評価（`docs/DB_DESIGN.md` 第5章）

---

## 1. 全体の流れ

```
 S0 分析を作る
  │
 S1 動画一覧を取る ──→ S2 属性・サムネを取る          （Win・ログイン不要。一覧と属性は続けて取る）
  │
 S3 集計・サンプル ──→ S4 AI に渡す形に整える         （コード）
  │
 S5 分類の軸を提案 ──→ ★H1 軸を確認                   （AI → 人）
  │
 S6 ラベル付け ──→ S7 段階の区切りと経路の下書き（自動で確定）
  │
 S8 代表動画を選ぶ（数字で自動に確定）
  │
 S9 コメントを取る                                   （Win・ログイン済み Chrome。1本約3分）
  │
 S10 コメントを整える ──→ S11 コメント分析            （コード → AI）
  │
 S12 レポートを書く ──→ S13 検算 ──→ ★H5 レポートを直す（修正案・人の考察を入れて、章ごとに書き直させる）
  │
 S14 媒体向けに仕上げる ──→ S15 納品物を出す
  │
（試験のときだけ）S16 採点・記事との比較
```

★は人の確認点（第3章）。代表の確認（H3）と、執筆前の考察の投入（H4）は置かない（ユーザー、2026-09-30）。**段階の確認（H2）も置かない**（同日。「AI への指示は界隈分類の確認以外は定型」）。走り出したら、人が止めるのは界隈分類の確認（H1）だけ。代表は数字で切れる。考察はレポートを見てから H5 で入れる。

## 2. 手順の詳細

### S0 分析を作る

| 項目 | 内容 |
|---|---|
| 誰が・どこで | 人が Web 画面で入力 → コードが分析フォルダを作る |
| 入力 | 楽曲名とアーティスト名、または TikTok の楽曲ページ URL |
| 処理 | 名前なら Web 検索で楽曲ページを探す（既存の `find_tiktok_music_url`）。分析 ID を決め、目録 `analysis.json` を作る。**知識ベースに未蒸留の記事がないか確かめる**（あれば運営に知らせ、この分析は今ある最新版で進める。`E2E_TODO.md` の K） |
| 出力 | 分析フォルダ、`analysis.json` |

### S1 動画一覧を取る

| 項目 | 内容 |
|---|---|
| 誰が・どこで | コード・Win（未ログインのヘッドレス Chrome） |
| 処理 | 楽曲ページのグリッドをスクロールして、並んだ動画の URL と数値を集める（既存 `scraper.py`） |
| 出力 | ① 一覧 CSV（13列: Index, URL, 投稿日, 本文, いいね, 共有, コメント数, 再生, 保存, リポスト, 種別, 投稿者, 曲名）／② 取得の記録 |
| 規模 | シルエットで880本 |
| 注意 | グリッドは推薦順で入れ替わる。**一覧を寝かせず、S2 まで続けて取る** |

### S2 属性とサムネイルを取る

| 項目 | 内容 |
|---|---|
| 誰が・どこで | コード・Win（未ログインのヘッドレス Chrome） |
| 処理 | 動画ページを1本ずつ開き、ページ内のデータから約40項目を取る（既存 `analysis/enrich.py`）。サムネは URL が24時間で失効するので画像をその場で保存 |
| 取るもの | 投稿者のフォロワー数・bio・認証、投稿地域、言語、TikTok のカテゴリラベル、提案語、画面上の文字、エフェクト、広告フラグ、尺、音源 |
| 出力 | ① 属性 JSONL、サムネ画像／② 取得の記録 |
| 所要 | 約3.2秒/本（880本で約47分） |
| 注意 | 削除済み・写真投稿は属性が取れない（シルエットで245本）。「取れなかった」と記録する |

### S3 集計とサンプル

| 項目 | 内容 |
|---|---|
| 誰が | コード（既存 `analysis/prep_sample.py`） |
| 処理 | 週ごとの本数と再生数、離陸週（週の本数が全体の5%を初めて超えた週）。分類対象の足切り（いいね1,000以上 または 再生1万以上）。軸を考えるための層化サンプル（再生上位100＋最初期40＋離陸後の各週から6本、乱数の種は固定）。ラベル付けの対象 |
| 出力 | ③ 週次表、サンプル、ラベル対象 |

### S4 AI に渡す形に整える

| 項目 | 内容 |
|---|---|
| 誰が | コード（既存 `analysis/build_llm_input.py`） |
| 処理 | 動画ごとに分類に効く項目だけ抜いた一覧、サムネの一覧画像（20枚を1枚に、番号つき。AI に画像を何百回も読ませないため） |
| 出力 | ③ AI への入力一式 |

### S5 分類の軸を提案する

| 項目 | 内容 |
|---|---|
| 誰が | AI（指示書 `classify_clean.md` の前半） |
| 入力 | S4 の層化サンプルとサムネ一覧、（あれば）知識ベース |
| 処理 | 5つの軸の値と定義を提案する: 界隈（誰が）／フォーマット（何をした）／動機（なぜこの曲）／地域／アカウント種別。各軸に「不明」を必ず入れる。**最初に事前知識を申告する** |
| 出力 | ④ 軸の案、事前知識の申告 |

### ★H1 軸を確認する（第3章）

値の統合・改名・追加・削除。例:「タレント」と「インフルエンサー」を分けるか。

### S6 ラベルを付ける

| 項目 | 内容 |
|---|---|
| 誰が | AI（指示書 `classify_clean.md` の後半） |
| 入力 | 確定した軸、ラベル対象の動画（属性＋サムネ） |
| 処理 | 1本ごとに5軸の値、確信度（H＝複数の手掛かりが一致／M＝1つ／L＝推測）、根拠を1行 |
| 出力 | ④ ラベル（E2E では200本） |
| 目安 | 確信度 H 57%／M 27%／L 16%（シルエット） |

### S7 段階の区切りと経路の下書き

| 項目 | 内容 |
|---|---|
| 誰が | コードが区切りの候補を出し → AI が名前を付けて経路を書く |
| 処理 | 週×界隈の表から、界隈の構成が入れ替わる週・離陸週・ピーク週を候補にする。AI が段階に名前を付け、各段階の代表を2〜3本挙げ、「再生数順では落ちるが経路上は重要な動画」を挙げる。観測と推測を分けて書く |
| 出力 | ④ 段階の区切りと経路の下書き（シルエットでは4段階） |

### （H2 段階の確認は置かない。2026-09-30）

### S8 代表動画を選ぶ（人の確認なしで確定）

| 項目 | 内容 |
|---|---|
| 誰が | コード（既存 `analysis/select_reps.py` を直して使う） |
| 処理 | セル＝界隈×段階。各セルに最低2本（そのセルの最初期1本＋最大再生1本）。残りはセルの規模の平方根に比例して配分。**必ず含める**: 起点動画、全体の最初期、公式・本人、全体の再生上位3本。**再生数で一括に切らない**（シルエットの起点は再生数順で59位だった） |
| コメント量 | 標準40件。起点・本家・公式・解説・大型ヒットは120件。返信は界隈で切り替え（見せる系の界隈は返信なし、それ以外は「返信数上位3件＋質問形＋本人・公式」の返信を各5件まで） |
| 時間予算 | 1回の取得は12時間まで。1本の見込み ≒ API 回数 ÷ 1.8回/分 ＋ 15秒（標準で約3分 → 約240本） |
| 出力 | ③ 代表のリスト（選んだ理由、コメント量、予想所要時間つき）。画面には出すが、確認は求めない |
| 到達性 | S9 のセッションでグリッドに見えている動画の中から選ぶ。見えない動画は同じセルの別の動画に差し替える（E2E では65本中38本がグリッドに無かった） |

### S9 コメントを取る

| 項目 | 内容 |
|---|---|
| 誰が・どこで | コード・Win（ログイン済みの捨てアカウントの Chrome、`spatest.py`） |
| 処理 | 楽曲ページのグリッドから代表動画を探して画面内で遷移し、コメント欄を開いてスクロールし、アプリが受け取ったデータを横取りする。返信は「返信を表示」を押して取る |
| 出力 | ① コメントの原本（1行＝動画1本、本体と返信）／② 取得の記録（動画ごとの API 回数、申告総数、混入の有無、描画状態） |
| 必ず見るもの | 混入0（コメントの動画 ID ＝ 対象の動画 ID）、20件ちょうどで止まっていない、画面遷移で取れている |
| 注意 | グリッドで見つからない動画は取れない（E2E では65本中38本）。**取れなかったと記録する**。途中で止まったら続きから再開する |

### S10 コメントを整える

| 項目 | 内容 |
|---|---|
| 誰が | コード（既存 `analysis/prep_comments.py`） |
| 処理 | 動画ごとに Markdown にする: 動画の属性（界隈・段階・投稿者・説明文・提案語）＋コメント（いいね順、ID つき）＋返信（親の下にぶら下げる）。本体に同梱された返信も拾う |
| 出力 | ③ 動画ごとのコメント Markdown |

### S11 コメントを分析する

| 項目 | 内容 |
|---|---|
| 誰が | AI（指示書 `analyze_comments_clean.md`）。**S12 とは別の実行にする**（合わせると AI に渡す量が50万トークンを超える） |
| 処理 | 動画ごとに: この界隈がなぜこの曲を取り上げたか、反応の型と割合、代表的なコメントの引用（ID つき）、投稿者の反応、返信から読めること、言語の比率。次に界隈ごとに束ねる。最初に事前知識を申告する |
| 出力 | ④ 動画ごとの分析、界隈ごとの統合、返信の価値のメモ、事前知識の申告 |

### S12 レポートを書く

| 項目 | 内容 |
|---|---|
| 誰が | AI（指示書 `write_report_clean.md`） |
| 入力 | S3・S7 の表と代表リスト、S11 の分析、知識ベース（用語集・文体ガイド。版を記録する）と、カードから選んだ近い過去レポート数本の全文。人の考察は入れない（H5 で入れる） |
| 処理 | 章ごとに書く。数値は表から引用し、AI に計算させない。推測は「推測」と書く |
| 出力 | ④ レポート（Markdown、内部 ID つき）、担当の注記 |

### S13 検算

| 項目 | 内容 |
|---|---|
| 誰が | コード |
| 処理 | 引用したコメント ID が実在するか、いいね数・再生数・本数が原本と一致するか、存在しない動画に触れていないか |
| 出力 | ④ 検算結果（不一致があれば H5 で示す） |

### ★H5 レポートを直す（第3章）

出来たレポートを利用者が読み、修正案と人の考察（音楽的特徴、切り出し箇所、時代背景、TikTok 外の指標、業界の知見など、データからは書けない部分）を入れる → AI が該当の章を書き直す。何度でも。

### S14 媒体向けに仕上げる

| 項目 | 内容 |
|---|---|
| 誰が | AI（指示書 `finish_note.md`） |
| 処理 | 内部 ID を消す、動画 URL を単独行にする（note で埋め込みになる）、試験用語を消す。著者が書き足す箇所の一覧を作る |
| 出力 | ④ 貼り付け用原稿、タイトル、変更の記録、書き足す箇所の一覧 |

### S15 納品物を出す

| 項目 | 内容 |
|---|---|
| 誰が | コード |
| 出力 | Excel 用 ZIP（動画 CSV は既存13列を先頭に、コメント CSV は1行1コメントで返信は親を指す）、原稿 |

### S16 採点と記事との比較（試験のときだけ）

| 項目 | 内容 |
|---|---|
| 誰が | AI（記事を読む担当は採点者だけ。指示書 `eval_rubric.md`、`compare_human_vs_ai.md`） |
| 出力 | ⑤ 採点、比較表 |

## 3. 人の確認点のやり方

> **2026-09-30 追記**: 利用者の AI をプラグインでつなぐ形（`docs/AI_ACCESS_UX.md` 第7章）では、確認は**会話の中**で行う（AI が案を見せ、利用者が返事する）。以下の「ダウンロード → 直してアップロード」は、Web 画面から直したい人向けの補助として残す。

**AI の案をファイルで書き出す → 利用者が手元で直す → アップロードする。** Web 画面で編集はさせない。画面に要るのは「ダウンロード」「アップロード」「案のまま確定」のボタンだけ。

| 確認点 | 書き出すもの | 形式 | 直すこと |
|---|---|---|---|
| H1 軸 | 軸の定義 | Markdown（軸ごとに見出し、値ごとに箇条書き） | 値の統合・改名・追加・削除 |
| H5 レポート | レポート本体と、AI が「ここは人の考察が要る」とした箇所の一覧 | Markdown | 本文を直す、章の冒頭に書き直しの指示や考察を書く |

アップロードの後の流れ:

1. 形を検査する（見出しが揃っているか、CSV の列が揃っているか、動画 URL が一覧にあるか）。**だめなら理由を返して、もう一度アップロードしてもらう**
2. AI の案との差分を画面に出す（何が変わったか）
3. 利用者が「確定」を押す → 次の Step に進む

確定したファイルは、AI の案とは別のファイルとして ④ に残す（案も消さない）。

## 4. AI をどこから持ってくるか

API は**追加料金**（Claude の Pro/Max プランに API は含まれず、Console で別にクレジットを買う）。そのため、決めてあった3つの経路のうち、利用者自身の定額プランを使う②③が主になる（`ANALYSIS_PIPELINE.md` 6b）。

| 経路 | 仕組み | 向く工程 |
|---|---|---|
| ① API キー | サーバーが自動で呼ぶ | 全工程を無人で（追加料金） |
| ② claude.ai・ChatGPT のコネクタ | サービスが道具（MCP サーバー）を出し、利用者が自分のチャットに登録して呼ぶ | 軸の提案・コメント分析・執筆など対話的な工程 |
| ③ 手元の Claude Code（Claudian 型） | 利用者の VS Code・Obsidian の Claude が同じ道具を呼ぶ | ラベル付けなど量の多い工程 |

どの経路でも AI の Step の中身は同じにする: **「指示書と入力を置く → AI が読んで出力を書く → サービスが検査して取り込む」**。
経路が違っても、AI が読むものと書くものは変わらない。疎通では Mac の Claude Code（私）が③の役をする。

## 5. 所要時間の目安（シルエット規模、880本）

| 工程 | 所要 |
|---|---|
| S1 一覧 | 数十分（グリッドのスクロール量次第） |
| S2 属性 | 約47分 |
| S3〜S8 | AI の工程を含めて数十分〜1時間（人の確認待ち・AI の番待ちは別） |
| S9 コメント | 代表の本数 × 約3分（65本なら約3時間、上限12時間） |
| S10〜S14 | 1〜2時間（人の確認待ちは別） |
