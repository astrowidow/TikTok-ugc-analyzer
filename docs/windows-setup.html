Phase 0 — テキスト共有路を作る

目的: Windows 側で長いコマンドを手打ちしなくて済むようにする。Windows には何もインストールしないし、何にもログインしない。

Mac 側（先にこちらを起動）

受け渡し用のサーバーを立てます。渡すだけでなく、Windows からの受け取りもできます。

python3 ~/workspace/TikTok-ugc-analyzer/docs/mac-share-server.py

以前の python3 -m http.server 8765 や旧版のサーバーが動いている場合は、 Ctrl+C で止めてからこちらを起動してください（同じ 8765 番を使うため）。 URL は変わりません。

このサーバーはリポジトリの docs/ を直接配信します。 手順書やスクリプトを直したら、コピー作業なしでそのまま反映されます （spatest.py など docs/ に無いものは ~/win-transfer/ からも探します）。

初回だけ macOS がファイアウォールの確認ダイアログを出します（「python への着信接続を許可しますか」）。 「許可」を押してください。 拒否すると Windows から繋がりません。 Mac のファイアウォールは現在 有効 です。

終わったら Ctrl+C で止めてください。立てっぱなしにすると同一LANの誰でもそのフォルダを読めます。

Windows 側 — 最初に管理者 PowerShell を開く

今日の作業は最初から最後まで、この1つの管理者ウィンドウで行います。 途中で普通の PowerShell に戻る場面はありません。

  1. Win+X を押す（スタートボタンを右クリックでも同じ）
  2. 「ターミナル (管理者)」 または 「Windows PowerShell (管理者)」 を選ぶ
  3. UAC の確認に「はい」

管理者で開くと作業フォルダが C:\Windows\System32 になります。 以降のコマンドは cd から始まるものが多いので、そのままコピーして使ってください。

Windows 側 — この手順書を開く

Chrome のアドレスバーにこれを打つだけです。

http://192.168.0.52:8765/

この手順書自体もそこにあります。

http://192.168.0.52:8765/windows-setup.html

以降、このページのコード欄は右上の「コピー」ボタンで取れます。 手打ちは不要です。

curl は使いません。 PowerShell の curl は Invoke-WebRequest のエイリアスで別物ですし、 curl.exe のほうも --data-binary "@ファイル" がパスに空白を含むと error encountered when reading a file で失敗し、原因が分かりません。 このページではすべて PowerShell 標準のコマンドだけで通します。

ここから Phase 0 の終わりまでは「参考」です。今は実行しなくて構いません。 Phase 1 のスクリプトはダウンロードも Mac への送信も自分でやるので、手で送る場面は当面ありません。 試す場合は、どのコード欄もそのまま実行して失敗しないように書いてあります。

参考: ファイルをダウンロードする場合

cd $env:USERPROFILE\Downloads
Invoke-WebRequest -Uri "http://192.168.0.52:8765/win-phase1-ssh.ps1" -OutFile "win-phase1-ssh.ps1" -UseBasicParsing
Invoke-WebRequest -Uri "http://192.168.0.52:8765/win-launch-chrome.bat" -OutFile "win-launch-chrome.bat" -UseBasicParsing

参考: 逆方向（Windows → Mac）に出力を送る

画面の文字を書き写す必要はありません。 PowerShell 標準の機能だけで Mac に送れます。 Windows 側には何もインストールしません。

ファイルを送る（1行目で送る用のファイルを作ってから送ります。ファイルを作らずに2行目だけ実行すると 「存在しないため検出できません」と言われます）:

"send test" | Set-Content "$env:TEMP\out.txt"
Invoke-RestMethod -Uri "http://192.168.0.52:8765/upload/out.txt" -Method Post -InFile "$env:TEMP\out.txt"

コマンドの出力を画面に出しながら同時に送る場合は、Tee-Object を挟みます （例では Get-Date を送っています。実際に使うときはそこを送りたいコマンドに置き換えます）:

$out = "$env:TEMP\out.txt"
Get-Date *>&1 | Tee-Object -FilePath $out
Invoke-RestMethod -Uri "http://192.168.0.52:8765/upload/out.txt" -Method Post -InFile $out

ファイルを作らず、文字列をそのまま送る:

Invoke-RestMethod -Uri "http://192.168.0.52:8765/upload/memo.txt" -Method Post -Body "send test"

成功すると saved: inbox/out.txt (NN bytes) と返ります。送られたものは Mac の ~/win-transfer/inbox/ に入り、サーバーの画面にも [受信] inbox/... と出ます。 以降このページで「Mac に送ってください」と書いてある箇所は、これのことです。

Phase 2 で SSH が通れば scp が使えるようになるので、この方法はそれまでの繋ぎです。

Phase 2 — SSH を有効にする

目的: Mac から私がこの機械を操作できるようにする。同時にローカルネット外からは届かないように絞る。

セキュリティの整理: sshd を起動しても、それはこの機械でポート22の待ち受けを始めるだけです。 インターネットから届くかどうかを決めているのはルーターで、ポート転送を設定していなければ外からは到達できません。 下の手順ではさらにファイアウォールをローカルネットに限定して二重に塞ぎます。

ここから先は管理者 PowerShell が必要です。 Add-WindowsCapability（OpenSSH サーバーの導入）は管理者権限なしでは失敗します。

管理者 PowerShell の開き方

  1. Win+X を押す（スタートボタンを右クリックでも同じ）
  2. 「ターミナル (管理者)」 または 「Windows PowerShell (管理者)」 を選ぶ
  3. UAC の確認に「はい」

管理者で開くと作業フォルダが C:\Windows\System32 に変わります。 必ず cd し直してください。

スクリプトで一括実行する（推奨）

cd $env:USERPROFILE\Downloads
Invoke-WebRequest -Uri "http://192.168.0.52:8765/win-phase1-ssh.ps1" -OutFile "win-phase1-ssh.ps1" -UseBasicParsing
powershell -ExecutionPolicy Bypass -File .\win-phase1-ssh.ps1

1行目のダウンロードは、既に落としてあってももう一度やってください（スクリプトを更新しているため）。

管理者でないまま実行した場合、スクリプトが検出して止まり、 「自動で管理者ウィンドウを開き直すか」を聞いてきます。y と答えれば新しいウィンドウで開き直します （-NoExit 付きなので出力は消えません）。

実行内容は %USERPROFILE%\win-phase1-ssh.log に残り、終了時に Mac へ自動送信されます（Phase 1 と同じ）。画面の文字を書き写す必要はありません。

もし 0x800f0954 で失敗したら: WSUS やグループポリシーで Windows Update が 制限されている環境で起きます。その場合は GitHub の Win32-OpenSSH リリースから手動導入する道があるので、 エラーメッセージごと報告してください。推測で回避策を試さないこと。

手でやる場合（スクリプトが失敗したとき）

こちらも管理者 PowerShell で実行してください。

Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd
Set-NetFirewallRule -Name "OpenSSH-Server-In-TCP" -RemoteAddress LocalSubnet
Get-NetFirewallRule -Name "OpenSSH-Server-In-TCP" | Get-NetFirewallAddressFilter
Get-NetTCPConnection -LocalPort 22 -State Listen

Windows 側は全部 OK なのに Mac から 22 番がタイムアウトするとき

2026-09-11 に実際に起きた状態。 sshd は Running、ルールは LocalSubnet、0.0.0.0:22 で Listen、 それでも Mac からは「タイムアウト」（3389 番は即応答）。Windows のファイアウォールが SSH だけ落としている。 ありがちなのは「ルールが Private/Domain 限定なのにネットワークが Public 扱い」だが、推測で直さず 下のスクリプトで診断と修正を1回でやる。ついでに Mac の公開鍵も登録する （毎回パスワードを打つ経路だと Mac 側から無人で操作できないため）。

cd $env:USERPROFILE\Downloads
Invoke-WebRequest -Uri "http://192.168.0.52:8765/win-phase2-fw.ps1" -OutFile "win-phase2-fw.ps1" -UseBasicParsing
powershell -ExecutionPolicy Bypass -File .\win-phase2-fw.ps1

やること: ルールのプロファイル・ネットワークの種類・22番の他ルール・サードパーティFWを表示 → OpenSSH のルールを「有効 / 全プロファイル / LocalSubnet 限定」に揃える → Mac の公開鍵を C:\ProgramData\ssh\administrators_authorized_keys に登録して ACL を締める → sshd 再起動 → ログを Mac へ自動送信。Mac 側の疎通確認は私がやります。

うまくいかないとき — まず状態を確定させる

「導入コマンドが成功したのに sshd サービスが存在しない」ことが実際に起きます。 この場合、原因が「導入できていない」のか「導入できたがサービスが登録されていない」のかで対処が全く違います。 推測で進めず、まずこれを実行してください。

$out = "$env:TEMP\diag.txt"
& {
  Get-WindowsCapability -Online -Name OpenSSH* | Select-Object Name,State
  Get-Service sshd,ssh-agent -ErrorAction SilentlyContinue | Select-Object Name,Status,StartType
  "sshd.exe         : " + (Test-Path "$env:SystemRoot\System32\OpenSSH\sshd.exe")
  "install-sshd.ps1 : " + (Test-Path "$env:SystemRoot\System32\OpenSSH\install-sshd.ps1")
  (Get-CimInstance Win32_OperatingSystem).Caption
  [System.Environment]::OSVersion.Version
} *>&1 | Tee-Object -FilePath $out
Invoke-RestMethod -Uri "http://192.168.0.52:8765/upload/diag.txt" -Method Post -InFile $out

画面にも出ますし、同時に Mac にも送られます（逆方向の送り方）。

結果ごとの意味

出力意味対処
State : NotPresent導入できていない。 導入コマンドが成功したように見えて失敗している本当のエラーを取りに行く。報告してください
State : Installed かつ sshd.exe : True かつサービスの行が出ない導入済みだがサービスが登録されていない。既知の状態同梱の公式登録スクリプトを実行（下記）
State : Installed だが sshd.exe : False導入が中途半端。再起動待ちの可能性再起動してから診断をやり直す
Caption が Home エディション、またはビルドが古いAdd-WindowsCapability 経由の OpenSSH が使えない可能性別の道を選ぶ。報告して判断を仰いでください

サービスだけが無い場合の対処

OpenSSH に同梱されている公式の登録スクリプトを実行します（別途ダウンロードするものではありません）。

& "$env:SystemRoot\System32\OpenSSH\install-sshd.ps1"
Get-Service sshd,ssh-agent | Select-Object Name,Status,StartType

これで sshd が出てくれば、Phase 2 のスクリプトを最初から流し直してください。

それでも駄目な場合、推測で回避策を試さないでください。 0x800f0954 は WSUS やグループポリシーで Windows Update が制限されている環境で出ます。 そういう管理下にある機械に別経路でサービスを入れるのは勝手に判断してよいことではないので、 診断の出力ごと報告してください。

Phase 3 — 既存の穴を塞ぐ

目的: この機械に TikTok のセッションCookie を置く前に、既に開いている口を閉じる。

確認済みの事実: GitHub の astrowidow/TikTok-ugc-analyzer は公開リポジトリで、 push 済みの develop（ca35d9d）に start.bat と main.py が含まれています。 そこには ngrok の固定ドメインと、パスワード ymafia / ymafia の両方が書かれています。

ngrok は NAT を迂回します（内側から外へトンネルを張るため、ルーターは何も守ってくれない）。 つまり ngrok を起動している間は、リポジトリを見た人が誰でも URL とパスワードを知っている状態です。

そしてこれから、この機械に利用者ごとの TikTok セッションCookie（＝アカウントへのフルアクセス権）を置きます。

コード側は環境変数で上書きできる作りになっています（main.py:28-29）。

setx UGC_USER "任意のユーザー名"
setx UGC_PASS "十分に長いパスワード"

setx は新しく開いたウィンドウにしか反映されません。設定後は PowerShell と start.bat のウィンドウを開き直してください。

あわせて、start.bat:166 がパスワードを画面に印字している点と、固定ドメインを公開リポジトリに置いたままでよいかは、別途判断が要ります（今日の作業には影響しません）。

Phase 4 — 環境を作る

目的: Python環境と、コメント取得スクリプトをこの機械に置く。

4-1. リポジトリを取得する

公開リポジトリなので認証は要りません。

cd $env:USERPROFILE
git clone https://github.com/astrowidow/TikTok-ugc-analyzer.git

git が無ければ、Chrome で https://github.com/astrowidow/TikTok-ugc-analyzer/archive/refs/heads/develop.zip を開いて展開してください。

4-2. Python環境を作る

リポジトリの start.bat が .venv の作成と requirements.txt の導入までやってくれます。 サーバーを起動せずに環境だけ作りたいので、まず local 付きで一度動かし、 [2/4] 準備できました。 まで進んだら Ctrl+C で止めます。

cd $env:USERPROFILE\TikTok-ugc-analyzer
.\start.bat local

Python が入っていない場合はここでエラーになるので、https://www.python.org/downloads/windows/ から 3.11 か 3.12 を入れてください。 インストール時に「Add python.exe to PATH」に必ずチェックを入れること。

4-3. コメント取得スクリプトを置く

spatest.py はリポジトリに入っていません（Mac の ~/tiktok-overnight/ にあります）。 Phase 0 の共有路か、Phase 2 の SSH 経由で私が送ります。

Windows 側に置き場を作っておいてください。

mkdir $env:USERPROFILE\tiktok-overnight

Phase 0 の共有路で取る場合（Mac 側で ~/win-transfer に配置済み）:

cd $env:USERPROFILE\tiktok-overnight
Invoke-WebRequest -Uri "http://192.168.0.52:8765/spatest.py" -OutFile "spatest.py" -UseBasicParsing

Phase 5 — Chrome を対話セッションで起動する

目的: 実ウィンドウを持った Chrome を、リモートデバッグポート付きで立ち上げる。ここが今回の山場です。

SSH から直接 Chrome を起動してはいけません。

Windows はセッションを分離するので、SSH セッションから起動した GUI アプリはコンソールのデスクトップを持ちません。 Chrome は起動はしますが描画を止め、コメントの仮想リストがスケルトンのままになり、 ブロックもエラーも出ないまま全動画が20件で終わります（引き継ぎ書 2-9）。

必ず schtasks の /IT（ログオン中のユーザーのセッションで対話的に実行）で起動してください。

5-1. 起動用バッチを置く

mkdir C:\tiktok-profiles
cd C:\tiktok-profiles
Invoke-WebRequest -Uri "http://192.168.0.52:8765/win-launch-chrome.bat" -OutFile "win-launch-chrome.bat" -UseBasicParsing

5-2. タスクとして登録して実行する

schtasks /Create /TN "tiktok-chrome" /TR "C:\tiktok-profiles\win-launch-chrome.bat" /SC ONCE /ST 00:00 /IT /F
schtasks /Run /TN "tiktok-chrome"

/IT が肝です。これが無いとセッション0で動いてしまい、上の事故が起きます。 /SC ONCE /ST 00:00 は「スケジュールでは動かさない（手動で /Run する）」ための指定です。

5-3. 起動できたか確認する

Get-NetTCPConnection -LocalPort 9222 -State Listen
Invoke-RestMethod -Uri "http://127.0.0.1:9222/json/version"
見るもの期待値
Get-NetTCPConnectionListen の行が出る
/json/version{"Browser":"Chrome/...","webSocketDebuggerUrl":...} が返る

スクリプト側は 127.0.0.1:9222 への TCP接続なので、SSH セッションから実行してもセッション分離の影響を受けません。 「Chrome の起動だけは対話セッション、スクリプトの実行は SSH でよい」という役割分担です。

Phase 6 — TikTok に手動ログイン

目的: 捨てアカウントでログインしたセッションを C:\tiktok-profiles\main に作る。1回だけ。
ここから TikTok にアクセスします。

まず「画面をどう見るか」を決める必要があります

モニタが無い機械なので、ログイン操作をするには画面が要ります。

案利点欠点
モニタとキーボードを一時的に繋ぐ一番確実で速い。今日の1回で済む物理的に用意する必要がある
VNC を入れる（UltraVNC / TightVNC）切断してもセッションがロックしない。今後の保守にも効く導入の手間。LANに口が増える
私が CDP でスクリーンショットを撮り、クリック位置を指示してもらう画面が用意できなくても進む。これから作る画面転送の手動版でもある遅い。CAPTCHA が出ると厳しい

RDP は使わないでください。 接続して切断するとセッションがロックされ、描画が止まります。 これは 2-9 の再現そのもので、無言で20件頭打ちになります。

Mac のプロファイルをコピーして持ってきても駄目です。 Chrome の Cookie は macOS では Keychain、Windows では DPAPI で暗号化されており、 OS をまたぐと復号できません（引き継ぎ書 2-2 と同じ理屈）。必ず Windows 上で改めてログインしてください。

ログインするときの注意

  • この用途専用の捨てアカウントを使うこと。 本人アカウントは使わない（引き継ぎ書 第10章）。 ログイン方式ではリスクが IP ban ではなくアカウント凍結に移ります
  • ログインは Phase 5 で起動した Chrome（C:\tiktok-profiles\main のプロファイル）で行うこと。 別のウィンドウで入っても、そのプロファイルには残りません
  • ログイン後、そのウィンドウは閉じずに残しておいてください。Phase 7 でそのまま使います

Phase 7 — 検証

目的: ディスプレイレスの Windows 機で、コメント取得が成立するかを確かめる。
ここから TikTok にリクエストを送ります。絶対に一気に本数を増やさないでください。

7-1. まず動画0本（--probe）

楽曲ページだけを開きます。動画は1本も開きません。

cd $env:USERPROFILE\tiktok-overnight
$PY = "$env:USERPROFILE\TikTok-ugc-analyzer\.venv\Scripts\python.exe"
& $PY spatest.py --port 9222 `
  --music-url "https://www.tiktok.com/music/%E3%83%97%E3%83%AD%E3%83%9D%E3%83%BC%E3%82%BA-7506899764786726928" `
  --probe --log probe.log --summary probe_summary.json

ここで必ず見るもの

ログの行正常な値違ったときの意味
描画状態:visibility=visible かつ フレーム=1以上★止まっている と出たら、そこで中断。Phase 5 の /IT かセッションのロックを疑う。この状態で先に進むと全部20件で終わる
楽曲ページ読み込み完了リンクが数十件0件ならログインか表示制限を疑う
チャレンジ画面出ないPlease wait... が25秒以上続いたらブロック。中断して1.5時間空ける

描画状態: が NG だった場合、ここで止めて報告してください。 本数を増やしても直りませんし、増やした分だけ無駄に TikTok を叩くことになります。

7-2. 動画1本だけ（--limit 1）

ペースは実証済みの設定よりさらに保守的にしてあります。

& $PY spatest.py --port 9222 `
  --music-url "https://www.tiktok.com/music/%E3%83%97%E3%83%AD%E3%83%9D%E3%83%BC%E3%82%BA-7506899764786726928" `
  --limit 1 --calls-per-min 1.8 --max-calls-per-min 2.0 `
  --interval 15 --jitter 0.5 --collect-scrolls 10 `
  --out win1.jsonl --log win1.log --summary win1_summary.json

ここで必ず見るもの

見るもの正常な値違ったときの意味
描画状態:visibility=visible / フレーム>0上と同じ
SPA=はい「いいえ」ならフルロードしている。ブロックが3〜4本で来る（引き継ぎ書 2-5b）
取得件数20件ちょうどで止まっていないことぴったり20件は 2-9 の典型的な症状。総数 と 続き も併せて見る
総数 / 続き記録されている「20件で止まった」が完走か取りこぼしかは、これが無いと区別できない

混入の検算（必ずやること）

引き継ぎ書 2-10 のとおり、ページは次の動画のコメントを先読みします。 aweme_id を照合しない限り、全部別動画のデータでも気づけません。

& $PY -c "import json;rows=[json.loads(l) for l in open('win1.jsonl',encoding='utf-8')];bad=sum(1 for r in rows for c in (r.get('comments') or []) if str(c.get('aweme_id'))!=r['video_id']);print(f'{len(rows)}本 / 混入{bad}件')"

混入0件 でなければ失敗です。

7-3. ここから先

7-1 と 7-2 が両方通ったら、そこで一度止めて報告してください。 本数を増やすかどうかは、結果を見てから決めます。

Phase 8 — Mac から繋げるようにする

目的: 以降の作業を私が Mac から流せるようにする。

Phase 2 が終わっていれば、私に次の2つを伝えてください。

  • Windows 機の IPアドレス（Phase 1 で確認した IPv4）
  • Windows の ユーザー名（whoami の出力）

これで ssh と scp が使えるようになり、spatest.py の更新もログの回収も私の側でできます。

なお、デバッグポート（9222）を LAN に公開する必要はありません。必要なら SSH のポート転送 （ssh -L 9222:127.0.0.1:9222 <user>@<win-ip>）で安全にトンネルできます。 デバッグポートをそのままネットワークに晒すのは、そのブラウザの無制限操作権を配ることと同じなので絶対にしないでください。

やってはいけないこと

やらないこと理由
ヘッドレス検知の回避（navigator.webdriver の偽装、UAの書き換え）引き継ぎ書 第4章で「やらないと決めた」こと。今回の方針は「検知されないようにする」ではなく「検知されるような状態を作らない」＝本当に実ウィンドウを持たせる、です
レート制限の閾値を探るテスト同じく第4章。403 は TikTok 側の明示的な停止シグナル
1つの Chrome（同じポート）に2つのスクリプトを同時接続する互いに干渉して両方の結果が壊れます。実際に事故が起きています（引き継ぎ書 第9章）
Mac 側と同時に収集を走らせる同一ネットワーク＝グローバルIPが同じなので、TikTok から見た1IPあたりの要求レートが単純に足し算になります
プロファイルをリポジトリに入れるセッションCookie はアカウントへのフルアクセス権そのもの。しかもこのリポジトリは公開です
結果を見ずに本数を増やすこの案件の失敗はすべて無言です。判定表を通してから進めること
